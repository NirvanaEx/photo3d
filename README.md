# photo3d

Инструмент превращения фотографии в 3D-модель, управляемый Claude через MCP.

Claude здесь не «кнопка запуска скрипта»: инструменты возвращают ему рендеры
результата картинками, поэтому он видит, что получилось, оценивает качество
и сам перезапускает генерацию с другими параметрами, пока модель не выйдет годной.

## Целевой цикл

```
фото → Claude оценивает кадр и препроцессинг
     → генерация меша на GPU
     → Blender: чистка, децимация, UV, текстура, экспорт
     → турнтейбл 4 ракурса → обратно в контекст Claude
     → Claude смотрит: дырки? поехавшая спина? размазанная текстура?
     → повтор с другим seed/параметрами ИЛИ выдача GLB пользователю
```

## Стек

| Слой | Чем |
|---|---|
| Генерация формы и текстур | TRELLIS.2 (MIT), 512³ — ровно под 12 ГБ |
| Удаление фона | BiRefNet / rembg |
| Постобработка | Blender headless (voxel remesh, Smart UV, bake, export, render) |
| Ремонт меша | pymeshlab (неманифолд, дыры, ошмётки) |
| UV-развёртка | xatlas |
| Интерфейс к Claude | MCP-сервер (Python, FastMCP) |
| Окружение | WSL2 + Docker + CUDA |

## Инструменты MCP

| Инструмент | Назначение |
|---|---|
| `photo_to_3d` | фото → GLB **+ рендеры сразу в контекст**; mode, seed, views |
| `smooth_model` | сгладить **на месте**: гранёность, ступеньки, рваный контур |
| `paint_model` | покрасить **на месте**: цвет или проекция фото, металл/шероховатость |
| `render_model` | перерендерить превью: стиль, число ракурсов, разрешение |
| `inspect_model` | полигоны, габариты, объём, замкнутость, вырожденные грани |
| `list_models` | последние модели, свежие сверху |
| `prepare_for_sculpting` | ремонт + перестройка в квады: база под лепку |
| `export_model` | положить GLB туда, где заберёт пользователь |
| `status` | движок, Blender, GPU, диск — первое при странном поведении |

### Принципы, по которым спроектирован API

Инструментами пользуется агент, а не человек за GUI. Отсюда:

1. **Один вызов — законченный результат.** `photo_to_3d` сам делает препроцесс,
   генерацию, экспорт и рендер. Обычный сценарий не требует цепочки из пяти вызовов.
2. **Картинки возвращаются в контекст.** Без этого агент слеп и способен лишь
   пересказывать чужие цифры вместо оценки результата.
3. **Короткие id, по умолчанию `last`.** Речь почти всегда о только что сделанной модели.
4. **Вызов блокирующий, без очередей и опроса статуса.** Подождать 60 секунд
   дешевле, чем жечь ходы на polling.
5. **Ошибка несёт подсказку, что делать дальше**, а не traceback. См. `server/errors.py`:
   каждая ошибка это «этап + причина + конкретное следующее действие».
6. **Пути принимаются в любом виде** — имя файла в `data/input`, POSIX-путь или
   windows-путь `D:\папка\фото.jpg`. Сервер живёт в WSL, называют файлы с обеих сторон.

## Подключение

`.mcp.json` в корне проекта регистрирует сервер, когда Claude Code открыт на этой папке.
Чтобы инструменты были доступны из любой директории:

```
claude mcp add -s user photo3d -- wsl.exe --cd /mnt/d/Develop/photo3d -e /opt/photo3d/venv/bin/python -m server.main
```

После регистрации Claude Code нужно перезапустить.

Проверка окружения целиком:

```
wsl -e /opt/photo3d/venv/bin/python /mnt/d/Develop/photo3d/scripts/selftest.py
```

## Стили рендера

| Стиль | Движок | Зачем | Скорость |
|---|---|---|---|
| `clay` | Workbench | оценка **формы**: глина с подчёркиванием впадин, без единой лампы | ~0.15 с/кадр |
| `color` | Workbench | быстро увидеть покраску, освещения нет | ~0.15 с/кадр |
| `beauty` | Cycles (CUDA) | показ результата: три источника света, подложка с тенью | ~1.7 с/кадр |

Отсутствие света в `clay` — не упущение, а смысл режима: настоящее освещение
прячет дыры и складки за бликами, а кадр снимается именно ради них.

### Почему постановочный рендер идёт на Cycles, а не на EEVEE

Вопреки ожиданиям, «быстрый» растеризатор здесь **в шесть раз медленнее**
трассировщика: EEVEE в WSL получает лишь программный GL-контекст и тратит
14.3 с на кадр, тогда как Cycles на CUDA — 1.7 с. Полный оборот из 24 кадров:
**45 с вместо 430 с**. Порядок движков в `STYLE_ENGINES` выставлен по этому замеру.

Чтобы GPU вообще стал доступен, пользователь WSL должен состоять в группе
**`render`**: узел `/dev/dri/renderD128` принадлежит `root:render` с правами
`crw-rw----`, и без членства EGL отваливается с `Permission denied`.
Членство применяется только после `wsl --shutdown`.

### Покраска

`paint_model` меняет модель **на месте**, не создавая новой карточки — открытый
веб-интерфейс перерисовывает именно её, поэтому человек за экраном видит
изменение сразу.

Два способа: сплошной PBR-материал (цвет, металличность, шероховатость) либо
проекция исходного кадра на модель. У проекции честное ограничение: бока и спина
получают растянутый цвет, одного ракурса на всю поверхность не хватает. Уйдёт
вместе с приходом TRELLIS.2 с его настоящими PBR-картами.

Палитра задана **sRGB-кодами**, а не линейными долями: линейные приходится
подбирать на глаз, и первая попытка дала «терракоту», которая рендерилась
блёклым лососевым. Там же причина, по которой постановочный стиль переключён
с AgX на `Standard`: AgX даёт красивую киношную картинку, но гасит насыщенные
цвета, а здесь важнее показать ту краску, которую действительно задали.

## Сглаживание

`smooth_model` убирает гранёность, ступеньки и рваный контур, меняя модель
на месте. Два метода: `preserve` (Corrective Smooth, силуэт почти не «сдувается»)
и `simple` (обычный Smooth — сильнее, но модель усыхает заметнее). Параметр
`subdivide` добавляет геометрию перед сглаживанием: силуэт становится
по-настоящему круглым ценой учетверения граней на каждый уровень.

Делается **в Blender, а не в pymeshlab**, и это принципиально: pymeshlab пишет
PLY и потерял бы материал с текстурой. Через Blender материалы, UV и покраска
доезжают до GLB целыми — сглаживать можно уже покрашенную модель.

Усадка габаритов считается и показывается честно: сглаживание всегда немного
стягивает объём, и это надо видеть, а не прятать. На тестовой модели при
силе 0.8 и двадцати проходах — 1.6–5.4% по осям.

Отдельно поправлена причина ступенек **в самой заглушке**: она строила высоту
прямо по расстоянию до края, которое растёт целыми шагами эрозии, отчего модель
выглядела контурной картой. Теперь поле размывается перед построением. Это
дефект заглушки, у настоящего генератора его не будет — но сам инструмент
сглаживания нужен и для реальных мешей после marching cubes.

## Подготовка под скульптинг

```
wsl -e /opt/photo3d/venv/bin/python /mnt/d/Develop/photo3d/scripts/test_sculpt.py <model_id> 5000
```

Сырой меш генератора для лепки не годится: треугольный суп после marching cubes,
разрывы, неманифолдная геометрия — подразделение по такому ломается. Цепочка:

1. **pymeshlab** — дубли, вырожденные грани, неманифолдные рёбра и вершины,
   мелкие несвязные ошмётки, закрытие дыр, согласование нормалей
2. **Blender Voxel Remesh** — перестройка оболочки целиком. Точечный ремонт не
   спасает меш с десятками разрывов, воксели дают замкнутый результат сразу в квадах
3. Плотность задаётся числом граней: грани ≈ 4.1 × divisions², после первого
   прохода делается одна корректировка по факту

Замер на тестовой модели: 393 неманифолдных ребра → 0, 20 572 треугольника →
**4842 грани, 100% квадов, замкнутая оболочка, 2.1 с**.

### Перенос внешнего вида

Перестройка даёт совершенно новую сетку, к которой старая UV-развёртка не
относится — без переноса покраска и текстура терялись бы при каждой
ретопологии. `prepare_for_sculpting` делает это сам (`keep_texture=True`),
выбирая путь по содержимому материала:

- **однородный материал** (цвет, металличность, шероховатость) — просто
  переносится. Развёртка не нужна, потерь нет, миллисекунды. Запекать
  равномерный цвет в текстуру было бы расточительно и хуже по качеству;
- **материал с картинкой** — на новой сетке строится развёртка
  (Smart UV Project) и запекается Cycles'ом «выделенное на активное», на GPU.

Результат проверяется по разбросу пикселей запечённой картинки: оператор
`bake` возвращает FINISHED и когда запёк пустоту.

Стиль превью наследуется от исходной модели — иначе перенесённая покраска
показывалась бы глиняной и было бы неясно, уцелела она или нет.

### Три грабли, на которые уже наступили

- **`libopengl0` обязателен**, хотя рендерить pymeshlab не должен. Без него Qt-плагины
  не грузятся и молча пропадают `meshing_close_holes`, изотропный ремешинг и запись
  в PLY. Импорт при этом проходит успешно, а причина видна только в stderr.
- **QuadriFlow не работает в фоновом режиме Blender.** На заведомо чистом меше
  (0 неманифолдных рёбер и вершин, 0 граничных, 1 остров) он отвечает
  «needs to be manifold and consistent normals» и возвращает FINISHED, не изменив
  ни одной грани. Воспроизводится в режимах FACES и RATIO, через `temp_override`
  и на триангулированном входе. Поэтому **результат проверяется по счётчику граней,
  а не по коду возврата** — это касается любого оператора Blender.
- **Оси при обмене через PLY.** glTF хранит Y вверх и его импортёр разворачивает
  сцену, PLY читается как есть. Цепочка GLB → pymeshlab → PLY → Blender давала
  модель, повёрнутую на 90°, и результат выглядел бесформенным комком при целой
  геометрии. Лечится явным `forward_axis="NEGATIVE_Z", up_axis="Y"`.

## Веб-интерфейс

```
wsl --cd /mnt/d/Develop/photo3d -e /opt/photo3d/venv/bin/python -m web.app
```

Открывается на <http://localhost:8765> — Windows достаёт до WSL через
localhostForwarding. Слушает только `127.0.0.1`: аутентификации нет, наружу нельзя.

Отдельный процесс от MCP-сервера, связи между ними никакой — только общая папка
`data/output`. Веб можно ронять и перезапускать, генерация не заметит.

Что внутри:

### Два режима просмотра

**3D** — `model-viewer`: вращение мышью, масштаб колесом, сдвиг правой кнопкой,
плюс кнопки приближения, сброса вида, автовращения, студийного фона и полного экрана.
Наклон камеры ограничен горизонтом — под пол ей незачем.

У живого вьюера **своя сцена**, и это не то же самое, что сцена в рендерах:
Blender-скрипты строят настоящую геометрию, а model-viewer показывает
исключительно содержимое GLB, добавить туда пол через него нельзя. Поэтому:

- **свет** — собственная HDR-панорама `web/static/studio.hdr` со схемой
  из Blender: ключевой сверху-слева, холодный заполняющий справа, тёплый
  контровой сзади. Генерируется `scripts/make_studio_hdr.py`.
  Именно HDR, а не JPEG: в LDR яркость упирается в единицу, бликов не возникает
  и подсветка выходит плоской. Здесь источники светят с яркостью до 26,
  из них 28% пикселей ярче единицы;
- **пол** — сетка в перспективе на `<canvas>`, а не градиент. Градиент читался
  просто как серое пятно: он не даёт ни ощущения плоскости, ни масштаба, ни
  понимания, куда повёрнута модель.
  Проецируется **матрицами самой камеры рендерера** (`projectionMatrix` и
  обратная `matrixWorld` из `viewer[Symbol(scene)]`), а не пересобранными
  из орбиты. Пересборка была ошибкой и давала сетку рядом с моделью:
  model-viewer вращает камеру вокруг начала координат и двигает сцену,
  см. `docs/PITFALLS.md`. Использование настоящих матриц снимает вопрос
  об осях, угле обзора и панорамировании целиком.
  Шаг сетки округляется до 1/2/5×10ⁿ так, чтобы модель занимала около шести
  клеток, дальние линии гаснут, под моделью рисуется круг-опора.
  Canvas лежит **под** `model-viewer`, и это заодно решает перекрытие: модель
  закрывает сетку сама, отдельная проверка глубины не нужна;
- **фон** — градиент CSS, изображающий студийный циклорам;
- **тень** — контактная тень самого `model-viewer`, включается вместе с фоном.

Кодировщик Radiance RGBE написан вручную (тридцать строк вместо зависимости).
Проверялся не собственным декодером — это сошлось бы само с собой, — а Blender'ом
как посторонним читателем: `scripts/check_hdr.py`.

**Турнтейбл** — вращение по 24 заранее отрендеренным кадрам полного оборота.
Не требует WebGL вообще: тянуть влево-вправо — вращать, колесо — масштаб,
Shift+тянуть — сдвинуть, двойной клик — сброс, стрелки — покадрово. Клик по
миниатюре в полосе доворачивает на этот ракурс.

Это не запасной костыль, а полноценный режим: кадры рендерятся Workbench'ем
с подчёркиванием впадин, поэтому рельеф на них читается лучше, чем при
освещении вьюера по умолчанию.

Если 3D-вьюер за восемь секунд не начал рисовать, интерфейс сам переключается
на турнтейбл и говорит об этом. Проверка терпеливая и с опросом, а не однократная:
тяжёлый GLB может рисоваться не сразу, и одна ранняя проверка уводила бы в
турнтейбл вполне работающий вьюер.

На диск пишется полный оборот из 24 кадров (`PHOTO3D_SPIN_FRAMES`), а в контекст
агента уходит равномерная выборка из четырёх: смотреть два десятка почти
одинаковых картинок бессмысленно, а место они занимают. Все кадры рендерятся
за один запуск Blender, поэтому 24 вместо 4 стоят около пяти секунд.

### Живое обновление

- **По SSE.** Сгенерированная модель появляется на открытой
  странице сама, без перезагрузки. Переключатель «следить за новыми» сразу
  открывает свежую — удобно, когда генерацию запускает агент, а смотрит человек.
- Обновления ловятся **опросом mtime раз в 800 мс, а не inotify**: папка лежит
  на `/mnt/d` (drvfs), где события файловой системы приходят ненадёжно.
- Интерактивный 3D-вьюер, полоса рендеров и исходное фото, лайтбокс по клику,
  стрелки ↑↓ для перехода между моделями.
- `model-viewer` **вендорнут** в `web/static/vendor/` (`scripts/fetch-vendor.sh`),
  а не подключён с CDN: интерфейс должен открываться без интернета и не меняться
  под ногами при обновлении пакета.

## Целевое железо

- RTX 3060 **12 ГБ** (Ampere, compute 8.6), драйвер 580.97
- 6 ядер / 12 потоков, **16 ГБ ОЗУ** ← основное узкое место
- Windows 11 + WSL2 (Ubuntu) + Docker

Следствия, зашитые в архитектуру:

- TRELLIS.2 на 12 ГБ работает в разрешении 512³ (8 ГБ хватает на 256³).
  1024³ и выше требуют 16–24 ГБ — это уже не наша карта
- **Hunyuan3D 2.1 для текстур не подходит:** генерация PBR требует 21 ГБ VRAM,
  полный пайплайн — 29 ГБ. Отсюда выбор TRELLIS.2, который отдаёт
  Base Color / Roughness / Metallic / Opacity сам, без второй модели
- WSL2 ограничивается 10–11 ГБ через `.wslconfig` + swap, иначе Windows задыхается
- Blender-стадия запускается **после** освобождения VRAM, не параллельно с генерацией
- Модель живёт в VRAM между запросами (холодный старт 40–60 с),
  выгружается по таймауту простоя, чтобы не занимать GPU впустую

Ожидаемое время генерации: **60–90 секунд** на модель.

## Структура

```
server/      MCP-сервер и определения инструментов
pipeline/    препроцессинг, генерация, blender-скрипты
web/         веб-интерфейс просмотра (Starlette + SSE + model-viewer)
docker/      образ с CUDA + PyTorch + Blender
scripts/     установка весов, проверки окружения
data/
  input/     исходные фото
  output/    готовые модели
  cache/     промежуточные артефакты
  weights/   веса моделей (~20–30 ГБ, не в git)
```
