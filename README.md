# photo3d

Инструмент превращения фотографии в 3D-модель, управляемый Claude через MCP.

Claude здесь не «кнопка запуска скрипта»: инструменты возвращают ему рендеры
результата картинками, поэтому он видит, что получилось, оценивает качество
и сам перезапускает генерацию с другими параметрами, пока модель не выйдет годной.

## Целевой цикл

```
фото → Claude оценивает кадр и препроцессинг
     → генерация меша на GPU
     → Blender: чистка, децимация, UV, текстура, экспорт
     → турнтейбл 4 ракурса → обратно в контекст Claude
     → Claude смотрит: дырки? поехавшая спина? размазанная текстура?
     → повтор с другим seed/параметрами ИЛИ выдача GLB пользователю
```

## Стек

| Слой | Чем |
|---|---|
| Генерация формы и текстур | TRELLIS.2 (MIT), 512³ — ровно под 12 ГБ |
| Удаление фона | BiRefNet / rembg |
| Постобработка | Blender headless (voxel remesh, Smart UV, bake, export, render) |
| Ремонт меша | pymeshlab (неманифолд, дыры, ошмётки) |
| UV-развёртка | xatlas |
| Интерфейс к Claude | MCP-сервер (Python, FastMCP) |
| Окружение | WSL2 + Docker + CUDA |

## Инструменты MCP

| Инструмент | Назначение |
|---|---|
| `check_photo` | что выйдет из кадра — **до** генерации, на процессоре, за секунды |
| `photo_to_3d` | фото → GLB **+ рендеры сразу в контекст**; mode, seed, views |
| `look_at` | один кадр с заданного ракурса, при желании крупным планом |
| `smooth_model` | сгладить **на месте**: гранёность, ступеньки, рваный контур |
| `paint_model` | покрасить **на месте**: цвет или проекция фото, металл/шероховатость |
| `render_model` | перерендерить превью: стиль, число ракурсов, разрешение |
| `inspect_model` | полигоны, габариты, объём, замкнутость, вырожденные грани |
| `list_models` | последние модели, свежие сверху |
| `prepare_for_sculpting` | ремонт + перестройка в квады: база под лепку |
| `shot_scene` | кадры из сцены Godot: как мир выглядит на самом деле |
| `export_model` | положить GLB туда, где заберёт пользователь |
| `status` | движок, Blender, GPU, диск — первое при странном поведении |

### Принципы, по которым спроектирован API

Инструментами пользуется агент, а не человек за GUI. Отсюда:

1. **Один вызов — законченный результат.** `photo_to_3d` сам делает препроцесс,
   генерацию, экспорт и рендер. Обычный сценарий не требует цепочки из пяти вызовов.
2. **Картинки возвращаются в контекст.** Без этого агент слеп и способен лишь
   пересказывать чужие цифры вместо оценки результата.
3. **Короткие id, по умолчанию `last`.** Речь почти всегда о только что сделанной модели.
4. **Вызов блокирующий, без очередей и опроса статуса.** Подождать 60 секунд
   дешевле, чем жечь ходы на polling.
5. **Ошибка несёт подсказку, что делать дальше**, а не traceback. См. `server/errors.py`:
   каждая ошибка это «этап + причина + конкретное следующее действие».
6. **Пути принимаются в любом виде** — имя файла в `data/input`, POSIX-путь или
   windows-путь `D:\папка\фото.jpg`. Сервер живёт в WSL, называют файлы с обеих сторон.

## Установка TRELLIS.2

Порядок важен: конфиг пересобирается под то, что уже скачано.

```
docker build -t photo3d/trellis:1 docker/
wsl -e /opt/photo3d/venv/bin/python scripts/fetch_trellis.py
wsl -e /opt/photo3d/venv/bin/python scripts/fetch_dinov3.py
```

Что происходит и почему именно так:

**Веса — 11 ГБ, а не 16.** Файлы разрешения 1024 пропускаются: режиму 512 они
не нужны. Просто не скачать их нельзя — `from_pretrained` перебирает **все**
ключи конфига и падает на отсутствующем файле, поэтому `fetch_trellis.py`
чинит и сам конфиг. Пересобрать его под другой режим:
`scripts/sync_config.py 512|1024|1024_cascade`.

**Веса лежат на `/opt/photo3d/weights`, а не в `data/`.** Это нативная ext4:
safetensors читаются через mmap, страницы вытесняются под нагрузкой, и 11 ГБ
весов уживаются с 10 ГБ ОЗУ. На `/mnt/d` через drvfs так не выходит.

**Кодировщик DINOv3 закрыт согласием Meta.** `fetch_dinov3.py` без ключей
берёт официальный источник, с `--mirror` — открытую копию, предварительно
сверив её хеши с официальными и проверив строение весов по `config.json`.

**Модель удаления фона намеренно не ставится.** Своя (`rembg`) уже есть, а
штатная весит 5.4 ГБ, требует некоммерческой лицензии и выполняет
`trust_remote_code=True`. При готовом альфа-канале пайплайн её не вызывает.

## Что получается, а что нет

Прогон шести примеров из репозитория TRELLIS.2 — сложные предметы, а не
силуэты: `scripts/test_examples.py`, итог в `data/cache/examples/итог.jpg`.

Прошли все шесть: **6.4–7.2 минуты**, видеопамять **2.62–3.85 ГБ**,
283–299 тысяч граней.

**Получается хорошо.** Ажурная корона с камнями в оправах. Танк с
проработанными гусеницами и стволами. Диорама комнаты — с мебелью, лестницей
и растениями внутри, при замкнутых стенах снаружи. Тонкие завитки
декоративного растения. Цвета и материалы переносятся верно.

**Не получается.** Плоский фрагмент стены с лозами модель замкнула в объём —
свернула плоскость в подобие бочки. Это не сбой сборки, а свойство задачи: по
одному кадру нельзя отличить плоский предмет от повёрнутого объёмного, и
модель выбирает замкнутую оболочку. Для плоских предметов такой инструмент не
годится.

**Свечение не переносится.** У танка стволы на снимке светятся, у модели —
обычный тёмный металл. Эмиссия не входит в набор карт
(Base Color / Roughness / Metallic / Opacity), и взяться ей неоткуда.

## Проверка кадра до генерации

`check_photo` снимает фон и показывает силуэт, который уйдёт в генератор,
вместе с замерами. Секунда-две процессорного времени против семи минут
видеокарты: половина неудач видна ещё здесь — предмет в двадцатую долю кадра,
обрезанный краем, два предмета вместо одного.

Правил всего три, и это результат замера, а не скромность. Изначально их было
шесть; на двенадцати примерах репозитория с известным исходом три отпали:

- **плоский предмет силуэтом не ловится.** Заведомо провальный кадр — фрагмент
  стены с лозами — по всем геометрическим признакам неотличим от удавшихся:
  заполнение рамки 0.56 против 0.24 у ажурного растения и 0.83 у диорамы
  комнаты, а вышли обе хорошо;
- **дисперсия лапласиана не отличает размытие от ровной заливки.** Чистый
  рисунок сердца даёт 27 при совершенно резком контуре, примеры — от 384 до
  7251. Порог здесь браковал бы студийные снимки, которые выходят лучше всего;
- **число кусков маски не равно числу предметов.** У ажурного растения маска
  честно распадается на 349 кусочков. Признак — только второй крупный кусок.

Поэтому инструмент возвращает **картинку силуэта на шахматке**, а не одни
числа: плоская стена на ней видна сразу, хотя ни одно число её не выдаёт.
Шахматка, а не сплошной фон, потому что на однотонном не отличить край
предмета от дырки в маске.

## Стили рендера

| Стиль | Движок | Зачем | Скорость |
|---|---|---|---|
| `clay` | Workbench | оценка **формы**: глина с подчёркиванием впадин, без единой лампы | ~0.15 с/кадр |
| `color` | Workbench | быстро увидеть покраску, освещения нет | ~0.15 с/кадр |
| `beauty` | Cycles (CUDA) | показ результата: три источника света, подложка с тенью | ~1.7 с/кадр |

Отсутствие света в `clay` — не упущение, а смысл режима: настоящее освещение
прячет дыры и складки за бликами, а кадр снимается именно ради них.

### Почему постановочный рендер идёт на Cycles, а не на EEVEE

Вопреки ожиданиям, «быстрый» растеризатор здесь **в шесть раз медленнее**
трассировщика: EEVEE в WSL получает лишь программный GL-контекст и тратит
14.3 с на кадр, тогда как Cycles на CUDA — 1.7 с. Полный оборот из 24 кадров:
**45 с вместо 430 с**. Порядок движков в `STYLE_ENGINES` выставлен по этому замеру.

Чтобы GPU вообще стал доступен, пользователь WSL должен состоять в группе
**`render`**: узел `/dev/dri/renderD128` принадлежит `root:render` с правами
`crw-rw----`, и без членства EGL отваливается с `Permission denied`.
Членство применяется только после `wsl --shutdown`.

### Крупный план и цена оборота

Два изменения об одном и том же: не платить полную цену рендера там, где она
не нужна.

**`look_at` снимает один кадр** с заданного ракурса — 3–6 секунд против 45 за
оборот. Превью показывает фигуру целиком в 512 точках, и на голову там
приходится десятков шесть: судить по такой картинке о лице нельзя, а
разглядеть замеченную дырку — тем более. Азимут совпадает с номерами кадров
превью, так что «кадр 090 странный» переводится в `azimuth=90` напрямую.

Приближает **длинный фокус, а не подъезд камеры**, и это не мелочь: чтобы
голова фигуры заполнила кадр, подъезжать пришлось бы внутрь описанной сферы —
оттуда лезет и отсечение ближней плоскостью, и перспективная карикатура
вместо портрета. Расстояние остаётся прежним, сужается угол объектива.

Сцена, свет и настройки движка у одиночного кадра и у оборота — общий код:
иначе крупный план показывал бы не то, что на превью, и сравнивать их было бы
нельзя. Проверено сверкой: кадр с параметрами по умолчанию совпадает с нулевым
кадром оборота попиксельно.

**`spin=False` у `paint_model` и `smooth_model`** рисует четыре кадра вместо
двадцати четырёх. Замер на реальной модели: **10.9 с против 55.3 с**, экономия
44 секунды на каждой пробе. Цвет и силу сглаживания подбирают итерациями, и
платить сорок пять секунд за каждую попытку незачем — оборот нужен
веб-интерфейсу для вращения перетаскиванием, а не агенту, которому в контекст
уходят те же четыре картинки.

Неполный оборот инструмент **говорит вслух**: иначе человек за экраном увидит
рваное вращение и пойдёт искать поломку там, где её нет. Вернуть полный —
`render_model(spin=True)` на удачном варианте.

### Покраска

`paint_model` меняет модель **на месте**, не создавая новой карточки — открытый
веб-интерфейс перерисовывает именно её, поэтому человек за экраном видит
изменение сразу.

Два способа: сплошной PBR-материал (цвет, металличность, шероховатость) либо
проекция исходного кадра на модель. У проекции честное ограничение: бока и спина
получают растянутый цвет, одного ракурса на всю поверхность не хватает. Уйдёт
вместе с приходом TRELLIS.2 с его настоящими PBR-картами.

Палитра задана **sRGB-кодами**, а не линейными долями: линейные приходится
подбирать на глаз, и первая попытка дала «терракоту», которая рендерилась
блёклым лососевым. Там же причина, по которой постановочный стиль переключён
с AgX на `Standard`: AgX даёт красивую киношную картинку, но гасит насыщенные
цвета, а здесь важнее показать ту краску, которую действительно задали.

## Сглаживание

`smooth_model` убирает гранёность, ступеньки и рваный контур, меняя модель
на месте. Два метода: `preserve` (Corrective Smooth, силуэт почти не «сдувается»)
и `simple` (обычный Smooth — сильнее, но модель усыхает заметнее). Параметр
`subdivide` добавляет геометрию перед сглаживанием: силуэт становится
по-настоящему круглым ценой учетверения граней на каждый уровень.

Делается **в Blender, а не в pymeshlab**, и это принципиально: pymeshlab пишет
PLY и потерял бы материал с текстурой. Через Blender материалы, UV и покраска
доезжают до GLB целыми — сглаживать можно уже покрашенную модель.

Усадка габаритов считается и показывается честно: сглаживание всегда немного
стягивает объём, и это надо видеть, а не прятать. На тестовой модели при
силе 0.8 и двадцати проходах — 1.6–5.4% по осям.

Отдельно поправлена причина ступенек **в самой заглушке**: она строила высоту
прямо по расстоянию до края, которое растёт целыми шагами эрозии, отчего модель
выглядела контурной картой. Теперь поле размывается перед построением. Это
дефект заглушки, у настоящего генератора его не будет — но сам инструмент
сглаживания нужен и для реальных мешей после marching cubes.

## Подготовка под скульптинг

```
wsl -e /opt/photo3d/venv/bin/python /mnt/d/Develop/photo3d/scripts/test_sculpt.py <model_id> 5000
```

Сырой меш генератора для лепки не годится: треугольный суп после marching cubes,
разрывы, неманифолдная геометрия — подразделение по такому ломается. Цепочка:

1. **pymeshlab** — дубли, вырожденные грани, неманифолдные рёбра и вершины,
   мелкие несвязные ошмётки, закрытие дыр, согласование нормалей
2. **Blender Voxel Remesh** — перестройка оболочки целиком. Точечный ремонт не
   спасает меш с десятками разрывов, воксели дают замкнутый результат сразу в квадах
3. Плотность задаётся числом граней: грани ≈ 4.1 × divisions², после первого
   прохода делается одна корректировка по факту

Замер на тестовой модели: 393 неманифолдных ребра → 0, 20 572 треугольника →
**4842 грани, 100% квадов, замкнутая оболочка, 2.1 с**.

### Перенос внешнего вида

Перестройка даёт совершенно новую сетку, к которой старая UV-развёртка не
относится — без переноса покраска и текстура терялись бы при каждой
ретопологии. `prepare_for_sculpting` делает это сам (`keep_texture=True`),
выбирая путь по содержимому материала:

- **однородный материал** (цвет, металличность, шероховатость) — просто
  переносится. Развёртка не нужна, потерь нет, миллисекунды. Запекать
  равномерный цвет в текстуру было бы расточительно и хуже по качеству;
- **материал с картинкой** — на новой сетке строится развёртка
  (Smart UV Project) и запекается Cycles'ом «выделенное на активное», на GPU.

Результат проверяется по разбросу пикселей запечённой картинки: оператор
`bake` возвращает FINISHED и когда запёк пустоту.

Стиль превью наследуется от исходной модели — иначе перенесённая покраска
показывалась бы глиняной и было бы неясно, уцелела она или нет.

### Три грабли, на которые уже наступили

- **`libopengl0` обязателен**, хотя рендерить pymeshlab не должен. Без него Qt-плагины
  не грузятся и молча пропадают `meshing_close_holes`, изотропный ремешинг и запись
  в PLY. Импорт при этом проходит успешно, а причина видна только в stderr.
- **QuadriFlow не работает в фоновом режиме Blender.** На заведомо чистом меше
  (0 неманифолдных рёбер и вершин, 0 граничных, 1 остров) он отвечает
  «needs to be manifold and consistent normals» и возвращает FINISHED, не изменив
  ни одной грани. Воспроизводится в режимах FACES и RATIO, через `temp_override`
  и на триангулированном входе. Поэтому **результат проверяется по счётчику граней,
  а не по коду возврата** — это касается любого оператора Blender.
- **Оси при обмене через PLY.** glTF хранит Y вверх и его импортёр разворачивает
  сцену, PLY читается как есть. Цепочка GLB → pymeshlab → PLY → Blender давала
  модель, повёрнутую на 90°, и результат выглядел бесформенным комком при целой
  геометрии. Лечится явным `forward_axis="NEGATIVE_Z", up_axis="Y"`.

## Веб-интерфейс

```
wsl --cd /mnt/d/Develop/photo3d -e /opt/photo3d/venv/bin/python -m web.app
```

Открывается на <http://localhost:8765> — Windows достаёт до WSL через
localhostForwarding. Слушает только `127.0.0.1`: аутентификации нет, наружу нельзя.

Отдельный процесс от MCP-сервера, связи между ними никакой — только общая папка
`data/output`. Веб можно ронять и перезапускать, генерация не заметит.

Что внутри:

### Разделы и навигация

Слева постоянная панель, три раздела, цифры `1`–`3` переключают:

- **Главная** — вся библиотека плиткой: миниатюра, движок, полигоны, размер на
  диске, возраст, родословная. Сверху сводка (сколько моделей, сколько занято,
  разбивка по движкам), поиск по имени/id/исходнику, фильтр по движку,
  сортировка — в том числе **по размеру**, потому что чаще всего разбирать
  библиотеку садятся именно тогда, когда кончилось место.
- **Просмотр** — тот самый вьюер, что и был, со своим списком слева.
- **Корзина** — удалённое, с возвратом и окончательным стиранием.

Разделы заданы **реестром** в начале `nav.js`: одна запись описывает пункт
панели, маршрут, заголовок и отрисовку. Добавить раздел — дописать запись,
а не править разметку, роутер и обработчики по отдельности.

Адрес живёт в хеше (`#/`, `#/m/<id>`, `#/trash`), поэтому на конкретную модель
можно дать ссылку и вернуться кнопкой «назад».

### Что можно делать с моделями

- **Удалить** — модель уезжает в `data/trash`, а не стирается. Причина та же,
  что записана в `scripts/cleanup.py`: место на диске есть, а вернуть
  передумав дешевле, чем восстанавливать шестиминутной генерацией. Стереть
  окончательно можно из корзины, отдельной кнопкой.
  Диалог показывает, сколько освободится, и предупреждает о двух вещах:
  модель **моложе пятнадцати минут** (по ней может идти работа) и у неё есть
  **производные** (останутся без исходника). Ради этого диалог свой, а не
  `confirm()`: системное окно ни того, ни другого не покажет, а решает именно
  это.
- **Выбрать несколько** и удалить пачкой — девять почти одинаковых попыток
  пересадки поштучно разбирать невесело.
- **Переименовать** и **отметить звёздочкой**: `m_0e7364` в голове не держится.
- **Переделать** — собирает готовый вызов и кладёт в буфер обмена. Для
  генерации это `photo_to_3d(...)` с тем же исходником и новым seed, для
  ретопологии — `prepare_for_sculpting(...)` с родителем и тем же числом
  граней. Чему инструмента нет (пересадка головы) — просьба словами.

Запускать генерацию сама страница **не умеет, и это намеренно**. Веб держится
в стороне от пайплайна ровно затем, чтобы его можно было ронять и
перезапускать посреди работы. Стань он вторым управляющим процессом — падение
вкладки стало бы падением генерации. Поэтому кнопка готовит вызов, а запускает
его агент.

### Кто какой файл пишет

В папке модели два файла метаданных, и у каждого один владелец:

| файл | пишет | что там |
|------|-------|---------|
| `meta.json` | пайплайн | движок, seed, полигоны, время, родословная |
| `ui.json` | веб | имя, заметка, звёздочка, когда удалена |

Разделение не косметическое: генерация идёт в соседнем процессе и может
писать в свою половину прямо сейчас. Веб в `meta.json` не пишет вовсе, и
двум программам нечего делить. `ui.json` обновляется через временный файл
и `os.replace`, чтобы обрыв записи не оставил огрызок JSON вместо имени.

### Три режима просмотра

**3D** — `model-viewer`: вращение мышью, масштаб колесом, сдвиг правой кнопкой,
плюс кнопки приближения, сброса вида, автовращения, студийного фона и полного экрана.
Наклон камеры ограничен горизонтом — под пол ей незачем.

**Свободная камера** (кнопка ✥ или клавиша `C`) — облёт от первого лица, как
персонажем: `WASD` — движение, мышь — обзор, `Q`/`E` — вниз-вверх, `Shift` —
быстрее, колесо — скорость, `Esc` — выход. Мышь захватывается указателем
(pointer lock), не удался захват — обзор работает перетаскиванием. Клавиши
читаются по `event.code`, а не по `event.key`: при русской раскладке `key`
даёт «ц», «ф», «ы», «в», и WASD молча перестал бы работать.

Свободной камеры у `model-viewer` нет вообще: он умеет только орбиту, где
камера смотрит в цель с расстояния `radius`. Полёт собирается из двух его
свойств сразу — интерфейс держит собственное состояние (глаз и углы взгляда)
и отдаёт вьюеру цель = глаз + направление·radius вместе с орбитой,
развёрнутой на 180°. Камера, которую вьюер вычислит из этой пары, встаёт
ровно в глаз, а поворот головы перестаёт таскать её по дуге вокруг модели.
Проверялось не на глаз: шаг `W` совпадает с направлением взгляда, а обзор
не сдвигает камеру ни на одну тысячную.

Что об этом стоит знать:

- **`radius` в режиме не меняется.** Соблазн «подъезжать» его уменьшением
  велик, но именно из него вьюер считает ближнюю и дальнюю плоскости, и
  радиус, уехавший от того, под который их посчитали, даёт отсечение не там.
  Едем целиком глазом, радиус — константа режима.
- **Дальняя плоскость ограничивает полёт**, и предел виден в подсказке. При
  штатном `auto` модель пропадала бы уже в четырёх своих габаритах от камеры
  (см. `docs/PITFALLS.md`), поэтому на время режима радиус в `max-camera-orbit`
  задаётся в десять габаритов. Дальше камеру просто не пускает — исчезнувшая
  без объяснения модель читается как поломка вьюера.
- **Обзор на время режима расширяется до 65°.** Штатный подбирается так, чтобы
  модель заполнила кадр, и выходит телеобъектив — 30° на типовой модели.
  Внутри сцены он даёт ровно две жалобы: мир прыгает при повороте (один пиксель
  мыши сдвигал картинку на четыре экранных) и «иду по колено в воде», потому
  что узкий угол сжимает перспективу и убивает ощущение хода.
- **Чувствительность мыши считается от фактического обзора**, а не задана в
  радианах на пиксель: отклик держится в долях кадра — 600 пикселей мыши на
  поворот в высоту кадра, то есть 1.14 экранного пикселя на мышиный.
- **Скорость привязана к габаритам модели**, а не к абсолютным единицам: GLB
  приходят и метровые, и сантиметровые, фиксированные м/с в одном случае
  стоят на месте, в другом улетают за горизонт с первого нажатия.
- **Выход возвращает ровно тот ракурс, с которого взлетели.** Свободная камера —
  временный режим, и «где я вообще» после выхода хуже, чем потеря налётанного
  вида. Кнопка сброса ⌖ в самом режиме не выкидывает из него, а разворачивает
  на модель и подтягивает к ней, если улетели далеко.

У живого вьюера **своя сцена**, и это не то же самое, что сцена в рендерах:
Blender-скрипты строят настоящую геометрию, а model-viewer показывает
исключительно содержимое GLB, добавить туда пол через него нельзя. Поэтому:

- **свет** — собственная HDR-панорама `web/static/studio.hdr` со схемой
  из Blender: ключевой сверху-слева, холодный заполняющий справа, тёплый
  контровой сзади. Генерируется `scripts/make_studio_hdr.py`.
  Именно HDR, а не JPEG: в LDR яркость упирается в единицу, бликов не возникает
  и подсветка выходит плоской. Здесь источники светят с яркостью до 26,
  из них 28% пикселей ярче единицы;
- **пол** — сетка в перспективе на `<canvas>`, а не градиент. Градиент читался
  просто как серое пятно: он не даёт ни ощущения плоскости, ни масштаба, ни
  понимания, куда повёрнута модель.
  Проецируется **матрицами самой камеры рендерера** (`projectionMatrix` и
  обратная `matrixWorld` из `viewer[Symbol(scene)]`), а не пересобранными
  из орбиты. Пересборка была ошибкой и давала сетку рядом с моделью:
  model-viewer вращает камеру вокруг начала координат и двигает сцену,
  см. `docs/PITFALLS.md`. Использование настоящих матриц снимает вопрос
  об осях, угле обзора и панорамировании целиком.
  Шаг сетки округляется до 1/2/5×10ⁿ так, чтобы модель занимала около шести
  клеток, дальние линии гаснут, под моделью рисуется круг-опора.
  Canvas лежит **под** `model-viewer`, и это заодно решает перекрытие: модель
  закрывает сетку сама, отдельная проверка глубины не нужна;
- **фон** — градиент CSS, изображающий студийный циклорам;
- **тень** — контактная тень самого `model-viewer`, включается вместе с фоном.

Кодировщик Radiance RGBE написан вручную (тридцать строк вместо зависимости).
Проверялся не собственным декодером — это сошлось бы само с собой, — а Blender'ом
как посторонним читателем: `scripts/check_hdr.py`.

**Турнтейбл** — вращение по 24 заранее отрендеренным кадрам полного оборота.
Не требует WebGL вообще: тянуть влево-вправо — вращать, колесо — масштаб,
Shift+тянуть — сдвинуть, двойной клик — сброс, стрелки — покадрово. Клик по
миниатюре в полосе доворачивает на этот ракурс.

Это не запасной костыль, а полноценный режим: кадры рендерятся Workbench'ем
с подчёркиванием впадин, поэтому рельеф на них читается лучше, чем при
освещении вьюера по умолчанию.

Если 3D-вьюер за восемь секунд не начал рисовать, интерфейс сам переключается
на турнтейбл и говорит об этом. Проверка терпеливая и с опросом, а не однократная:
тяжёлый GLB может рисоваться не сразу, и одна ранняя проверка уводила бы в
турнтейбл вполне работающий вьюер.

На диск пишется полный оборот из 24 кадров (`PHOTO3D_SPIN_FRAMES`), а в контекст
агента уходит равномерная выборка из четырёх: смотреть два десятка почти
одинаковых картинок бессмысленно, а место они занимают. Все кадры рендерятся
за один запуск Blender, поэтому 24 вместо 4 стоят около пяти секунд.

**Прогулка** — ходьба по сцене от первого лица: `WASD`, мышь, `Space` — прыжок,
`Shift` — бежать, `Esc` — отпустить мышь. Человеческий масштаб: рост камеры
1.65 м, тяжесть, столкновения. Предмет стоит на полу в натуральную величину —
видно ровно то, как он будет выглядеть в игре.

**Это отдельный рендерер на three.js, а не режим `model-viewer`.** Причина
записана правилом в `CLAUDE.md`: тот показывает ПРЕДМЕТ, его камера всегда
орбитальная, наружу он её не отдаёт и переписывает каждый кадр из своих
сферических координат. Ходьба туда не встраивается ничем, а в three.js она
есть готовой. Взято готовым:

| Что | Откуда |
|---|---|
| захват мыши и обзор | `PointerLockControls` |
| столкновения и «не пройти сквозь» | `Octree` + `Capsule` из примера `games/fps` |
| загрузка GLB | `GLTFLoader` |
| студийный свет | `HDRLoader` + `PMREMGenerator` из той же `studio.hdr` |
| пол и туман | `GridHelper`, `THREE.Fog` |

Своего — склейка с интерфейсом, посадка модели на пол и показания панели.
Заметно, что три вещи, стоившие в вьюере отдельной возни, здесь однострочные:
сетка пола (вместо холста с матрицами камеры), растворение её края туманом
(вместо двух градиентов поверх) и доступ к камере (вместо приватных символов).

Зависимости лежат в `web/static/vendor/three/`, версия **прибита** (0.185.1):
аддоны живут в одном репозитории с ядром и совместимости между версиями им
никто не обещает. Кладёт их `scripts/fetch-vendor.sh three`. Сборщика в
проекте нет и не заводится — голое имя `three` разрешает **карта импортов**
в `index.html`, штатный способ обойтись без сборки.

**Столкновения по геометрии — только для лёгких сцен.** Замер сборки
октодерева:

| Что | Треугольников | Время |
|---|---|---|
| ровная сфера | 16 000 | 199 мс |
| скан TRELLIS | 40 000 | 3 943 мс |
| скан TRELLIS | 296 000 | больше двух минут, вкладка не отвечает |

Линейной цены нет: на плотной сканированной сетке треугольники попадают сразу
во много узлов, и дерево дробится глубже — 12 мкс на треугольник против 98.
Поэтому выше 12 000 треугольников столкновения считаются по габаритному ящику,
и панель пишет, каким коллайдером сейчас пользуется. Рукотворные лёгкие сцены
(та же локация из `pipeline/blender/corridor.py`) получают честную геометрию.

**Локации отличаются от предметов по габаритам** (выше 2.2 м и шире 4 м) и
ведут себя иначе: игрок ставится **внутрь**, в середину пола, лицом вдоль
длинной оси, а пол-подставка, сетка и подсветка гасятся — у локации всё своё.
Предмет наоборот обходят снаружи, встав на полтора его габарита.

Локацию сначала надо выгрузить в GLB — `corridor.py` оставляет `.blend` и
кадры Cycles, ходить по ним нельзя. Шага два, и первый пропускать нельзя:

```
blender -b data/output/loc_corridor/corridor.blend --factory-startup -noaudio \
  -P pipeline/blender/bake_scene.py -- --out data/output/loc_corridor/corridor_baked.blend
```

```
blender -b data/output/loc_corridor/corridor_baked.blend --factory-startup -noaudio \
  -P pipeline/blender/export_glb.py -- --out data/output/m_corridor/model.glb
```

Коридор выходит 2756 треугольников — ниже порога, поэтому столкновения по
честной геометрии: игрок упирается в торец на 7.11 м от центра при внутренней
длине 14.3 м, в стены на ±1.23 м, и застревает в шкафчиках, если идёт вплотную
к левой стене. Всё это измерено пошаговым прогоном физики, а не «побегал».

**Процедурные материалы в GLB не переносятся — и не «плоскими цветами», а
белыми.** Доски пола и штукатурка нарисованы шумами прямо в шейдере, а glTF
знает только Principled BSDF с картинками и константами. Экспортёр узлы не
сворачивает, он **выбрасывает вход целиком**: замер первой выгрузки — восемь
материалов из одиннадцати без `baseColorFactor` вовсе, то есть белые по
умолчанию формата. Уцелели ровно три, у которых цвет был константой.

Поэтому `bake_scene.py` переводит шум в текстуру, и только после него имеет
смысл экспорт. Что он делает и почему именно так:

- **развёртка строится на материал, а не на объект.** Материал у нескольких
  объектов общий, и разверни каждого в свои 0..1 — они запекутся друг поверх
  друга в одну картинку. Все объекты материала правятся разом, Smart UV
  Project раскладывает их в общий атлас;
- **разрешение считается от площади** (256 пикселей на метр, потолок 2048²).
  Стены коридора — 352 м², дверные ручки все вместе — 0.5 м²: одинаковый
  размер картинки для них означал бы либо кашу на стенах, либо мегабайты
  впустую на ручках. Реально вышло 2048² и 256²;
- **узел-приёмник во время запекания не подключён к шейдеру.** Подключённый
  даёт обратную связь: Cycles читает Base Color, там ещё пустая картинка, и
  запекается пустота в пустоту. Провода перекидываются после;
- **свет в текстуру не запекается** (`pass_filter={"COLOR"}`) — тени в
  текстуре остались бы навсегда, а сцену в прогулке освещает своё солнце
  из GLB;
- **шероховатость запекается отдельным проходом**, но только там, где она
  процедурная: пол, шкафчики, ручки. Металличность процедурной нигде не
  оказалась, а прохода запекания под неё и нет — случись такое, инструмент
  скажет вслух, а не подсунет молча константу;
- **бугорок (Bump) не переносится**: он не входит в набор запекаемых входов,
  и рельеф досок в прогулке остаётся нарисованным, а не выпуклым.

Итог замера: семь материалов, десять картинок, GLB 0.2 → 11.9 МБ, запекание
на CUDA. Каждая картинка проверена по разбросу пикселей — `bake` возвращает
FINISHED и запекая пустоту.

Панель слева внизу — заготовка dev-панели: положение, скорость, опора,
кадры в секунду, размер модели, коллайдер. Наружу модуль отдаёт `window.walk`
с намеренной отладочной ручкой `walk.debug`: пошаговый прогон физики
(`step`), нажатие клавиш (`press`), поворот (`look`) и вся сцена (`scene()`).
Именно ею проверено, что скорость шага равна заявленным 4.2 м/с, бег — 9.4,
а капсула упирается в модель ровно на её габарите плюс свой радиус.

### Живое обновление

- **По SSE.** Сгенерированная модель появляется на открытой
  странице сама, без перезагрузки. Переключатель «следить за новыми» сразу
  открывает свежую — удобно, когда генерацию запускает агент, а смотрит человек.
- Обновления ловятся **опросом mtime раз в 800 мс, а не inotify**: папка лежит
  на `/mnt/d` (drvfs), где события файловой системы приходят ненадёжно.
- Обход папок **вынесен в поток** и идёт по дешёвым отпечаткам: четыре `stat`
  на модель вместо перебора двух десятков кадров, а карточка пересобирается,
  только если её отпечаток изменился. На drvfs один `stat` стоит миллисекунды,
  и наивная сборка списка занимала почти секунду — в цикле событий такому не
  место, всё остальное ждало бы её. Замеры и обоснование замены перебора
  кадров одним `stat` — в комментарии к `_stamp` в `web/app.py`.
- Правка `ui.json` тоже попадает в отпечаток: переименование в одной вкладке
  должно доехать до остальных, а `meta.json` оно не трогает.
- Интерактивный 3D-вьюер, полоса рендеров и исходное фото, лайтбокс по клику,
  стрелки ↑↓ для перехода между моделями.
- `model-viewer` **вендорнут** в `web/static/vendor/` (`scripts/fetch-vendor.sh`),
  а не подключён с CDN: интерфейс должен открываться без интернета и не меняться
  под ногами при обновлении пакета.

### Почему изменяющие запросы требуют своего заголовка

Пока интерфейс только показывал, подделывать запросы к нему было незачем.
С появлением кнопки «удалить» — есть: чужая открытая вкладка может отправить
`POST` на `localhost:8765`, и браузер сам приложит заголовок Basic-авторизации,
если пароль задан. Модель уехала бы в корзину без ведома хозяина.

Поэтому все `POST` требуют заголовка `X-Photo3D: 1`. Форму или картинку с
чужого сайта отправить можно, а `fetch` с нестандартным заголовком браузер
сперва спросит предполётным `OPTIONS` — на который сервер не отвечает.
Токен в страницу класть не нужно: сам заголовок межсайтовому запросу
недоступен.

Идентификатор модели проверяется **шаблоном целиком** (`m_` и дальше только
цифры и строчные латинские), а не «начинается с `m_`»: он подставляется в путь,
и `..` внутри него увело бы раздачу файлов в соседние папки `data/`.

## Мост в Godot

Библиотека показывает предмет. Мир — сцены со светом, атмосферой, ходьбой,
анимациями и скриптами — собирается в Godot, и это не «ещё один вьюер», а
разделение обязанностей: перечисленное есть в любом движке готовым и чинилось
там пятнадцать лет, а генерация ассетов агентом с обратной связью картинками
не написана нигде. photo3d остаётся фабрикой, Godot — миром.

Godot выбран за то, что **сцены и ресурсы у него лежат текстом** (`.tscn`,
`.tres`, `.gd`): агент правит их так же, как правит код, без GUI и без плагина.
Свет и атмосфера — обычные свойства `WorldEnvironment`, то есть две строки в
файле. Весит движок 170 МБ одним exe без установщика, GLB импортирует нативно.

**Движок запускается с Windows-стороны, а не из WSL.** Внутри WSL графика
достаётся программным контекстом — тем самым, из-за которого EEVEE проиграл
Cycles в шесть раз. С Windows Godot видит RTX 3060 напрямую, а WSL исполняет
`.exe` через interop; переводится только путь (`wslpath`).

```
python -m bridge.import_asset [model_id]
```

Кладёт GLB в `game/assets/models/`, запускает импорт и **проверяет результат
счётчиками**, а не кодом возврата: Godot, как и Blender, сообщает об успехе и
тогда, когда сцена вышла пустой. Ноль треугольников — ошибка с подсказкой, а
не «импортировано».

Замеры разведки на этой машине:

| | коридор | модель TRELLIS |
|---|---|---|
| размер GLB | 11.3 МБ | 47.1 МБ |
| треугольников | 2 756 | 118 929 |
| материалов | 10 | 2 |
| габариты | 3.80 × 4.00 × 15.70 м | 0.69 × 1.01 × 0.47 м |
| импорт + разбор | 10.7 с | 24.1 с (повтор 5.0 с) |

Масштаб в метрах и оси сохраняются, запечённые карты Base Color, Roughness и
Metallic доезжают. **Normal и Emission — ноль на всех проверенных моделях**,
и терять их нечего: бугорок не входит в набор запекаемых входов
(`bake_scene.py`), эмиссия — в набор карт TRELLIS. Это долг фабрики, а не
потеря движка.

Кадр из мира снимается за 2.2–4.4 с вместе со стартом движка — дешевле любого
рендера в пайплайне. Но **только с окном**: в `--headless` кадров не рисуется
вовсе, и наивное ожидание отрисовки висит вечно, см. `docs/PITFALLS.md`.
Импорт и разбор геометрии, наоборот, headless работают.

В git уезжает всё, кроме самих ассетов и кэша импорта: они воспроизводятся
мостом из `data/output`, а что из какой модели собрано — записано в
`game/assets.json`.

### Глаза в мире

`shot_scene` запускает сцену, снимает её и возвращает кадры в контекст — то
же, чем `photo_to_3d` отличается от «скрипта, который сделал файл». По тексту
`.tscn` не видно, стоит ли предмет на полу или висит в воздухе и не съел ли
туман дальнюю стену.

Замер на сцене с коридором и моделью (121 685 треугольников): **один кадр —
3.3 с, пять кадров — 3.6 с**. Движок стартует один раз, поэтому ракурсы почти
бесплатны. Локация осматривается изнутри, с высоты глаз, поворотом на месте —
то же правило, что в прогулке; предмет облетается снаружи.

Вместе с кадрами возвращаются **замеры сцены, ошибки скриптов и яркость
каждого источника света**. Последнее не украшение: коридор выгорал в белое,
и объяснение «текстуры не доехали» было бы неверным — виновато солнце
**внутри GLB** с яркостью 28 686 (Blender пишет люксы, Godot читает их как
множитель). В тексте сцены этого источника не видно вовсе, а в отчёте съёмки
видно сразу. Подробности и лечение — в `docs/PITFALLS.md`.

Съёмка идёт **с окном**: в `--headless` кадров не рисуется вовсе. Окно живёт
три секунды и закрывается само.

### Ассет, пригодный для игры

Сгенерированная модель в игру не ставится как есть: 119 тысяч треугольников —
цена не столько отрисовки, сколько **столкновений**, а там она нелинейна
(замер в вебе: 16 000 треугольников — 199 мс на дерево, 40 000 — 3.9 с,
296 000 вешают вкладку). Поэтому `pipeline/gameready.py` кладёт в один GLB два
меша: видимый, ужатый до бюджета, и грубую оболочку с суффиксом **`-colonly`**.

Суффикс — соглашение импортёра Godot: узел с таким именем превращается в
`StaticBody3D` с телом столкновения, а сам меш из сцены убирается. Столкновения
не пишутся и не настраиваются, они приезжают вместе с ассетом. Проверяется это
замером, а не верой: разбор ассета печатает `тел 1, форм 1`.

```
python -m bridge.import_asset m_corridor   # + gameready=True в вызове
```

| | коридор | модель TRELLIS |
|---|---|---|
| треугольников было / стало | 2 756 / 2 756 | 118 929 / 20 000 |
| оболочка столкновений | 2 000 | 900 |

Коридор не тронут намеренно: он уже в бюджете, а децимация «на всякий случай»
только портит форму. Децимация — плата за превышение, а не обряд.

**Свет и камеры из ассета выбрасываются**, и это решение, а не побочный
эффект: свет — художественное решение уровня, и жить он должен в тексте сцены,
где его видно. Иначе повторяется история с солнцем в 28 686 люкс, которое
правится вслепую. Параметры выброшенного при этом **печатаются** — направление
солнца локации не подберёшь на глаз, и оно переносится в сцену числом.

### Ходьба

`game/scripts/player.gd` — `CharacterBody3D` с теми же числами, что в
веб-прогулке (4.2 м/с, бег ×2.2, тяжесть 24, рост камеры 1.65): одна локация
должна ощущаться одинаково в браузере и в игре. Клавиши читаются **физические**
(`is_physical_key_pressed`) — при русской раскладке WASD дают «цфыв», и в вебе
на это уже наступали.

Столкновений в коде нет ни строчки: тело даёт `CharacterBody3D`, оболочку —
сам ассет.

Проверяется это **пошаговым прогоном физики**, а не «побегал — вроде нормально»:

```
python -m bridge.walk_probe walk 300
```

Прогон ведёт игрока программно и печатает, на каком шаге он встал на опору,
сколько прошёл и из чего состоят тела столкновений. Замер на коридоре: опора
на 13-м шаге, по свободной дорожке **13.16 м до торца**, по дорожке с моделью —
упор через 2.02 м, ровно на габарите её коллайдера плюс радиус капсулы. Первый
же прогон нашёл ошибку, которую кадр показал бы как «почему-то черно»: игрок
появлялся за торцом коридора и падал двести метров вниз.

Прогон работает в `--headless`, и это не спорит с граблей про кадры: физика
идёт своим циклом и отрисовки не требует.

**Честное состояние на сейчас: коридор в игре тёмный.** Причина найдена и
записана — оконное стекло уехало в GLB непрозрачным (`alphaMode=OPAQUE`), то
есть окна работают как заложенные проёмы. Лечится в экспорте локации, а не в
сцене.

## Целевое железо

- RTX 3060 **12 ГБ** (Ampere, compute 8.6), драйвер 580.97
- 6 ядер / 12 потоков, **16 ГБ ОЗУ** ← основное узкое место
- Windows 11 + WSL2 (Ubuntu) + Docker

### Про «нужно 24 ГБ»

В README самого TRELLIS.2 написано, что нужна карта не меньше 24 ГБ. Это
относится к наивной загрузке всех блоков сразу и к каскаду 1536³. Устройство
модели другое: три отдельных DiT по 1.3B работают **последовательно**, а
режим `low_vram` (включён по умолчанию) возвращает каждый на CPU сразу после
использования. Резидентен всегда один — 2.6 ГБ в bf16.

**Замер на RTX 3060, режим 512:**

| | |
|---|---|
| пик видеопамяти | **2.62 ГБ** из 12 |
| загрузка весов с диска | 111 с |
| генерация | 224 с |
| экспорт GLB с текстурой 2048 | 25 с |
| на выходе | 185 282 вершины, 293 642 грани |

Требования к железу стоит проверять замером, а не принимать на веру.

Прочие следствия, зашитые в архитектуру:

- **Hunyuan3D 2.1 для текстур не подходит:** генерация PBR требует 21 ГБ VRAM,
  полный пайплайн — 29 ГБ. Отсюда выбор TRELLIS.2, который отдаёт
  Base Color / Roughness / Metallic / Opacity сам, без второй модели
- Веса лежат на **нативной ext4**, а не на `/mnt/d`: safetensors читаются через
  mmap, страницы вытесняются под нагрузкой, и 11 ГБ весов уживаются с 10 ГБ ОЗУ
  (замер: RSS процесса 5.2 ГБ). Через drvfs так не выходит
- WSL2 ограничивается 10 ГБ через `.wslconfig` + 8 ГБ swap, иначе Windows задыхается
- Blender-стадия запускается **после** освобождения VRAM, не параллельно с генерацией

## Структура

```
server/      MCP-сервер и определения инструментов
pipeline/    препроцессинг, генерация, blender-скрипты
web/         веб-интерфейс (Starlette + SSE + model-viewer)
  app.py     маршруты, отпечаток состояния, раздача файлов
  library.py корзина, ui.json, родословная, размеры
  static/    app.js — вьюер, nav.js — навигация и главная
game/        проект Godot: мир, свет, сцены
  scenes/    .tscn — пишутся текстом, редактор не нужен
  tools/     разбор ассета и прочая обвязка для запуска без человека
  assets/    ассеты из data/output (не в git), опись в assets.json
bridge/      перенос ассетов из библиотеки в игру, перевод путей WSL ↔ Windows
docker/      образ с CUDA + PyTorch + Blender
scripts/     установка весов, проверки окружения
data/
  input/     исходные фото
  output/    готовые модели
  trash/     удалённые модели, ждут возврата (не в git)
  cache/     промежуточные артефакты
  weights/   веса моделей (~20–30 ГБ, не в git)
```
