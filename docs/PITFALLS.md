# Грабли

Каждая запись — симптом, причина, лечение. Симптом стоит первым намеренно:
искать здесь будут по нему, а не по названию причины.

Все они настоящие: собраны по ходу работы, а не выписаны из документации.

---

## Половина pymeshlab отсутствует, PLY не сохраняется

**Симптом.** `import pymeshlab` проходит, но `meshing_close_holes`,
изотропного ремешинга и реконструкции Пуассона нет. `save_current_mesh`
падает с `Unknown format for save: ply`. В stderr — строки вида
`Cannot load library libfilter_meshing.so: (libOpenGL.so.0: cannot open shared object file)`.

**Причина.** Qt-плагины pymeshlab требуют `libOpenGL.so.0`, даже когда
ничего не рендерится. Без неё они молча не загружаются, а импорт при этом
проходит успешно.

**Лечение.** `apt-get install libopengl0`. Проверять наличие фильтра через
`hasattr(ms, name)` и сообщать о пропуске вслух, а не проглатывать.

## QuadriFlow ничего не делает, но рапортует об успехе

**Симптом.** `bpy.ops.object.quadriflow_remesh(...)` возвращает `FINISHED`,
число граней не меняется. В warning: `The mesh needs to be manifold and have
face normals that point in a consistent direction`.

**Причина.** В фоновом режиме Blender (`-b`) QuadriFlow не работает.
Проверено на заведомо чистом меше: 0 неманифолдных рёбер, 0 неманифолдных
вершин, 0 граничных, 1 остров — отказ всё равно. Воспроизводится в режимах
`FACES` и `RATIO`, через `context.temp_override` и на триангулированном входе.
Сообщение про манифолд вводит в заблуждение.

**Лечение.** Использовать Voxel Remesh — он даёт замкнутую оболочку целиком
из квадов за доли секунды. Шире: **результат операторов `bpy.ops` проверять
по счётчикам, а не по коду возврата.**

## После ремонта модель превратилась в бесформенный комок

**Симптом.** Геометрия по всем метрикам отличная — нужное число граней, все
квады, замкнутая оболочка, — а на рендере вместо объекта невнятная масса.

**Причина.** Оси при обмене через PLY. glTF хранит Y вверх, и его импортёр
разворачивает сцену в Z-вверх. PLY читается как есть, без поворота. Цепочка
GLB → pymeshlab → PLY → Blender давала модель, повёрнутую на 90°: турнтейбл
снимал её в профиль при совершенно целой геометрии.

**Лечение.** `bpy.ops.wm.ply_import(filepath=..., forward_axis="NEGATIVE_Z", up_axis="Y")`.
Шире: при обмене между форматами оси задавать явно, а результат смотреть
глазами — метрики этой ошибки не показывают вообще.

## Cycles считает на процессоре, кадр идёт 18 секунд

**Симптом.** Постановочный рендер 24 кадров занимает семь минут. В логе
`libEGL warning: failed to open /dev/dri/renderD128: Permission denied`.

**Причина.** Две независимые. Первая: пользователь WSL не состоит в группе
`render`, а узел принадлежит `root:render` с правами `crw-rw----`. Вторая:
Blender по умолчанию считает Cycles на CPU, GPU надо выбрать явно.

**Лечение.** `usermod -aG render <user>` плюс `wsl --shutdown` (без перезапуска
членство не применяется). В скрипте — выбрать устройство:
`prefs.compute_device_type = "OPTIX"` или `"CUDA"`, затем `scene.cycles.device = "GPU"`.
Итог: 45 секунд вместо 430.

## EEVEE медленнее Cycles

**Симптом.** «Быстрый» растеризатор даёт 14.3 с/кадр, трассировщик — 1.7 с.

**Причина.** В WSL EEVEE получает лишь программный GL-контекст. Cycles идёт
через CUDA и видеокарту не теряет.

**Лечение.** Для постановочных кадров первым пробовать Cycles, EEVEE держать
запасным. Общий вывод: **ожидания о производительности проверять замером.**

## Цвет выходит блёклым, не тем, что задали

**Симптом.** Заказана терракота, отрендерился бледный лосось.

**Причина.** Две сложились. Blender 4.x применяет вид `AgX`, который красиво
приглушает насыщенные цвета. И палитра была задана линейными долями «на глаз»
вместо честного перевода из sRGB.

**Лечение.** `scene.view_settings.view_transform = "Standard"` для кадров, где
важна достоверность цвета. Палитру задавать sRGB-кодами и переводить в
линейное пространство формулой.

## Элемент с атрибутом `hidden` виден на странице

**Симптом.** `el.hidden === true`, а элемент на экране. Полноэкранный оверлей
лайтбокса висит поверх всего интерфейса.

**Причина.** `hidden` задаёт `display: none` с крайне низким приоритетом,
и любое правило вроде `.lightbox { display: grid }` его перебивает.

**Лечение.** `[hidden] { display: none !important; }` в начале стилей.

## model-viewer загрузил модель, но ничего не рисует

**Симптом.** `loaded === true`, `modelIsVisible === false`, холст остался
300×150, в консоли `rAF timed out in updateSource`.

**Причина.** Окно не композитит кадры, поэтому `requestAnimationFrame` и
`ResizeObserver` не срабатывают. Ленивая загрузка и рендер завязаны на них.

**Лечение.** `loading="eager"` снимает половину проблемы. Полностью —
не лечится, это свойство среды. В интерфейсе предусмотрен откат на турнтейбл
по готовым кадрам, работающий без WebGL. Диагностический вывод: **прежде чем
чинить код, проверь, не врёт ли среда.**

## Наложенная графика не совпадает с 3D-моделью

**Симптом.** Сетка пола и круг-опора нарисованы в правильной перспективе, но
стоят не под моделью, а рядом. При панорамировании расхождение растёт.

**Причина.** Камера собиралась заново из `getCameraOrbit()` и `getCameraTarget()`.
Model-viewer вращает камеру **вокруг начала координат** и смещает саму сцену,
а не наоборот. Прибавление цели к позиции камеры даёт промах: небольшой в покое
(0.09 по Y на тестовой модели) и равный всему сдвигу после панорамирования.
Вдобавок `scene.boundingBox` хранится в своём пространстве, а в мир его
переводит `scene.target.position` — без этой поправки центр модели промахивается
мимо центра экрана.

**Лечение.** Не пересобирать камеру, а взять её у рендерера:
`viewer[Symbol(scene)].camera`, оттуда `projectionMatrix` и обратная
`matrixWorld`. Мировая точка = координата ящика + `scene.target.position`.
Тогда никакие соглашения об осях, FOV и панорамировании не имеют значения —
используется ровно то преобразование, которым рисуется модель.

Это внутренности библиотеки, и они могут измениться. Поэтому при их отсутствии
сетка не рисуется вовсе: **лучше без пола, чем пол не там, где модель.**

**Отдельный вывод про проверку.** Первая версия была проверена картой canvas
и признана рабочей: линии сходились к горизонту, перспектива считалась верно.
Но на карте была **только сетка, без модели**, поэтому несовпадение увидеть
было нечем. Проверять надо взаимное расположение, а не каждый объект отдельно:
в карту добавлена проекция габаритов модели, и центр обязан попадать в центр
экрана, а основание — внутрь круга.

## pip-пакет установился, но падает при первом вызове

**Симптом.** `rembg` ставится, при использовании — `No onnxruntime backend found`.
`trimesh.fix_normals()` — `ModuleNotFoundError: scipy`.

**Причина.** У обоих ключевые зависимости вынесены: у rembg в экстра `[cpu]`,
у trimesh графовые операции требуют scipy отдельно.

**Лечение.** `pip install "rembg[cpu]" scipy`. Шире: проверять пакет вызовом
той функции, ради которой он ставился, а не одним `import`.

## PowerShell калечит команды для wsl

**Симптом.** `wsl -e python -c "import x; print(\"y\")"` падает с
`SyntaxError: invalid syntax`, аргументы разъезжаются. `grep -r "..." $VAR/path`
с пустой переменной уходит рекурсивно обходить текущую папку.

**Причина.** Разбор аргументов нативных команд в PowerShell переставляет
кавычки непредсказуемо.

**Лечение.** Не передавать сложные строки инлайном. Класть код в файл-скрипт
и запускать его:
`wsl -e /opt/photo3d/venv/bin/python /mnt/d/.../script.py`.
Для shell-скриптов помогает `tr -d '\r' < файл | bash` — заодно снимает CRLF.

## Команда не найдена при запуске через `wsl -e`

**Симптом.** `wsl -u root -e usermod ...` → `execvpe usermod failed 2`.

**Причина.** `-e` запускает программу напрямую, без инициализации окружения,
поэтому `/usr/sbin` в PATH отсутствует.

**Лечение.** Полный путь (`/usr/sbin/usermod`) либо `wsl -e bash -lc "..."`.
