# Грабли

Каждая запись — симптом, причина, лечение. Симптом стоит первым намеренно:
искать здесь будут по нему, а не по названию причины.

Все они настоящие: собраны по ходу работы, а не выписаны из документации.

---

## Половина pymeshlab отсутствует, PLY не сохраняется

**Симптом.** `import pymeshlab` проходит, но `meshing_close_holes`,
изотропного ремешинга и реконструкции Пуассона нет. `save_current_mesh`
падает с `Unknown format for save: ply`. В stderr — строки вида
`Cannot load library libfilter_meshing.so: (libOpenGL.so.0: cannot open shared object file)`.

**Причина.** Qt-плагины pymeshlab требуют `libOpenGL.so.0`, даже когда
ничего не рендерится. Без неё они молча не загружаются, а импорт при этом
проходит успешно.

**Лечение.** `apt-get install libopengl0`. Проверять наличие фильтра через
`hasattr(ms, name)` и сообщать о пропуске вслух, а не проглатывать.

## QuadriFlow ничего не делает, но рапортует об успехе

**Симптом.** `bpy.ops.object.quadriflow_remesh(...)` возвращает `FINISHED`,
число граней не меняется. В warning: `The mesh needs to be manifold and have
face normals that point in a consistent direction`.

**Причина.** В фоновом режиме Blender (`-b`) QuadriFlow не работает.
Проверено на заведомо чистом меше: 0 неманифолдных рёбер, 0 неманифолдных
вершин, 0 граничных, 1 остров — отказ всё равно. Воспроизводится в режимах
`FACES` и `RATIO`, через `context.temp_override` и на триангулированном входе.
Сообщение про манифолд вводит в заблуждение.

**Лечение.** Использовать Voxel Remesh — он даёт замкнутую оболочку целиком
из квадов за доли секунды. Шире: **результат операторов `bpy.ops` проверять
по счётчикам, а не по коду возврата.**

## После ремонта модель превратилась в бесформенный комок

**Симптом.** Геометрия по всем метрикам отличная — нужное число граней, все
квады, замкнутая оболочка, — а на рендере вместо объекта невнятная масса.

**Причина.** Оси при обмене через PLY. glTF хранит Y вверх, и его импортёр
разворачивает сцену в Z-вверх. PLY читается как есть, без поворота. Цепочка
GLB → pymeshlab → PLY → Blender давала модель, повёрнутую на 90°: турнтейбл
снимал её в профиль при совершенно целой геометрии.

**Лечение.** `bpy.ops.wm.ply_import(filepath=..., forward_axis="NEGATIVE_Z", up_axis="Y")`.
Шире: при обмене между форматами оси задавать явно, а результат смотреть
глазами — метрики этой ошибки не показывают вообще.

## Cycles считает на процессоре, кадр идёт 18 секунд

**Симптом.** Постановочный рендер 24 кадров занимает семь минут. В логе
`libEGL warning: failed to open /dev/dri/renderD128: Permission denied`.

**Причина.** Две независимые. Первая: пользователь WSL не состоит в группе
`render`, а узел принадлежит `root:render` с правами `crw-rw----`. Вторая:
Blender по умолчанию считает Cycles на CPU, GPU надо выбрать явно.

**Лечение.** `usermod -aG render <user>` плюс `wsl --shutdown` (без перезапуска
членство не применяется). В скрипте — выбрать устройство:
`prefs.compute_device_type = "OPTIX"` или `"CUDA"`, затем `scene.cycles.device = "GPU"`.
Итог: 45 секунд вместо 430.

## EEVEE медленнее Cycles

**Симптом.** «Быстрый» растеризатор даёт 14.3 с/кадр, трассировщик — 1.7 с.

**Причина.** В WSL EEVEE получает лишь программный GL-контекст. Cycles идёт
через CUDA и видеокарту не теряет.

**Лечение.** Для постановочных кадров первым пробовать Cycles, EEVEE держать
запасным. Общий вывод: **ожидания о производительности проверять замером.**

## Цвет выходит блёклым, не тем, что задали

**Симптом.** Заказана терракота, отрендерился бледный лосось.

**Причина.** Две сложились. Blender 4.x применяет вид `AgX`, который красиво
приглушает насыщенные цвета. И палитра была задана линейными долями «на глаз»
вместо честного перевода из sRGB.

**Лечение.** `scene.view_settings.view_transform = "Standard"` для кадров, где
важна достоверность цвета. Палитру задавать sRGB-кодами и переводить в
линейное пространство формулой.

## Элемент с атрибутом `hidden` виден на странице

**Симптом.** `el.hidden === true`, а элемент на экране. Полноэкранный оверлей
лайтбокса висит поверх всего интерфейса.

**Причина.** `hidden` задаёт `display: none` с крайне низким приоритетом,
и любое правило вроде `.lightbox { display: grid }` его перебивает.

**Лечение.** `[hidden] { display: none !important; }` в начале стилей.

## model-viewer загрузил модель, но ничего не рисует

**Симптом.** `loaded === true`, `modelIsVisible === false`, холст остался
300×150, в консоли `rAF timed out in updateSource`.

**Причина.** Окно не композитит кадры, поэтому `requestAnimationFrame` и
`ResizeObserver` не срабатывают. Ленивая загрузка и рендер завязаны на них.

**Лечение.** `loading="eager"` снимает половину проблемы. Полностью —
не лечится, это свойство среды. В интерфейсе предусмотрен откат на турнтейбл
по готовым кадрам, работающий без WebGL. Диагностический вывод: **прежде чем
чинить код, проверь, не врёт ли среда.**

## pymeshlab падает на модели с текстурой

**Симптом.** `save_current_mesh("x.ply")` бросает
`Image .../texture_0 cannot be saved. Your MeshLab version has not plugin to
save file format`, следом в консоль сыплется `malloc_consolidate(): unaligned
fastbin chunk detected`. На той же модели без текстуры всё работает.

**Причина.** Сохраняя PLY, pymeshlab пытается записать рядом и встроенную
картинку. Имя текстуры из GLB (`texture_0`) идёт без расширения, формат он не
определяет и падает — повреждая кучу в придачу.

**Лечение.** Отдавать в pymeshlab **чистую геометрию**: сначала
`trimesh.load(glb, force="mesh").export("geometry.ply")`, потом уже загружать
её. Для ремонта и ретопологии внешний вид всё равно не нужен — он переносится
отдельным шагом с оригинала.

## Canvas с `inset: 0` не растягивается на родителя

**Симптом.** Наложенная на 3D-вид сетка смещена и отмасштабирована не так,
как модель. `getBoundingClientRect()` холста показывает 300×150 при родителе
990×451.

**Причина.** Canvas — **замещаемый элемент**. У таких `width: auto` разрешается
в собственный размер содержимого, а не растягивается по `inset: 0`, как у
обычных блоков. Задание только `canvas.width` (буфера) меняет и CSS-бокс,
поэтому при `devicePixelRatio ≠ 1` бокс расходится с родителем в те же разы.

**Лечение.** Явные `width: 100%; height: 100%` в CSS. Буфер задавать
как `размер × dpr`, а рисовать через `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`
в CSS-пикселях.

**Отдельно про проверку.** Ошибку дважды пропустила проверка «центр модели
попадает в центр экрана»: центр остаётся центром при **любом** масштабе по
горизонтали, поэтому такой тест слеп к ошибкам масштаба и аспекта. Проверять
надо точки **вне** центра, а лучше — прямо сравнивать прямоугольники холста
и родителя.

## Наложенная графика не совпадает с 3D-моделью

**Симптом.** Сетка пола и круг-опора нарисованы в правильной перспективе, но
стоят не под моделью, а рядом. При панорамировании расхождение растёт.

**Причина.** Камера собиралась заново из `getCameraOrbit()` и `getCameraTarget()`.
Model-viewer вращает камеру **вокруг начала координат** и смещает саму сцену,
а не наоборот. Прибавление цели к позиции камеры даёт промах: небольшой в покое
(0.09 по Y на тестовой модели) и равный всему сдвигу после панорамирования.
Вдобавок `scene.boundingBox` хранится в своём пространстве, а в мир его
переводит `scene.target.position` — без этой поправки центр модели промахивается
мимо центра экрана.

**Лечение.** Не пересобирать камеру, а взять её у рендерера:
`viewer[Symbol(scene)].camera`, оттуда `projectionMatrix` и обратная
`matrixWorld`. Мировая точка = координата ящика + `scene.target.position`.
Тогда никакие соглашения об осях, FOV и панорамировании не имеют значения —
используется ровно то преобразование, которым рисуется модель.

Это внутренности библиотеки, и они могут измениться. Поэтому при их отсутствии
сетка не рисуется вовсе: **лучше без пола, чем пол не там, где модель.**

**Отдельный вывод про проверку.** Первая версия была проверена картой canvas
и признана рабочей: линии сходились к горизонту, перспектива считалась верно.
Но на карте была **только сетка, без модели**, поэтому несовпадение увидеть
было нечем. Проверять надо взаимное расположение, а не каждый объект отдельно:
в карту добавлена проекция габаритов модели, и центр обязан попадать в центр
экрана, а основание — внутрь круга.

## pip-пакет установился, но падает при первом вызове

**Симптом.** `rembg` ставится, при использовании — `No onnxruntime backend found`.
`trimesh.fix_normals()` — `ModuleNotFoundError: scipy`.

**Причина.** У обоих ключевые зависимости вынесены: у rembg в экстра `[cpu]`,
у trimesh графовые операции требуют scipy отдельно.

**Лечение.** `pip install "rembg[cpu]" scipy`. Шире: проверять пакет вызовом
той функции, ради которой он ставился, а не одним `import`.

## PowerShell калечит команды для wsl

**Симптом.** `wsl -e python -c "import x; print(\"y\")"` падает с
`SyntaxError: invalid syntax`, аргументы разъезжаются. `grep -r "..." $VAR/path`
с пустой переменной уходит рекурсивно обходить текущую папку.

**Причина.** Разбор аргументов нативных команд в PowerShell переставляет
кавычки непредсказуемо.

**Лечение.** Не передавать сложные строки инлайном. Класть код в файл-скрипт
и запускать его:
`wsl -e /opt/photo3d/venv/bin/python /mnt/d/.../script.py`.
Для shell-скриптов помогает `tr -d '\r' < файл | bash` — заодно снимает CRLF.

## Модель загрузилась, но у неё «нет атрибута layer»

**Симптом.** `AttributeError: 'DINOv3ViTModel' object has no attribute 'layer'`
на первой же генерации. Веса при этом читаются, архитектура сходится.

**Причина.** TRELLIS.2 обходит слои кодировщика напрямую: `self.model.layer`.
В transformers 5.x они переехали внутрь энкодера и лежат по адресу
`model.model.layer`. Репозиторий писался в ноябре 2025, библиотека с тех пор
ушла вперёд.

**Лечение.** Не откатывать библиотеку, а подменить один метод. Сигнатуры
`embeddings(pixel_values, bool_masked_pos)` и
`layer(hidden_states, position_embeddings=...)` в новой версии те же -
проверено через `inspect.signature`, - поэтому расхождение ровно одно.
См. `patch_dino_layers()` в `pipeline/trellis/run_trellis.py`: список слоёв
ищется сначала по старому адресу, затем по новому.

**Общий вывод.** Когда чужой код лезет во внутренности библиотеки, ломается
он при её обновлении, а не при своём. Прежде чем откатывать версию целиком,
стоит сравнить сигнатуры: расхождение обычно точечное.

## Модель выглядит испачканной, хотя геометрия чистая

**Симптом.** На лице и других гладких местах тёмные разводы, будто модель
уронили в грязь. Форма при этом вылеплена аккуратно.

**Как проверить.** Отрендерить глиной, без текстуры. Если разводы пропали -
дело не в геометрии, а в раскраске. Пока эту проверку не сделали, объяснения
строились вокруг формы («линии рисунка вдавливаются в рельеф») и вели не туда.

**Причина.** Развёртка строится автоматически по сетке из marching cubes:
у каждого треугольника свой лоскут, между лоскутами - незаполненный чёрный
фон. При сглаживании текстуры фон затекает внутрь лоскутов. Чем мельче
лоскут, тем больше доля затёкшего.

Считается просто: `размер_карты^2 / число_граней` - это площадь на
треугольник.

| граней | карта | пикселей на грань | вид |
|---|---|---|---|
| 300 000 | 2048 | ~14 | грязь на гладких местах |
| 80 000 | 4096 | ~210 | чисто |

**Лечение.** Не гнаться за числом граней. 80 000 на карту 4096 выглядят
заметно лучше, чем 300 000 на 2048, **при том же времени работы** и вчетверо
меньшем файле. Значения в `server/config.py`, по режимам - в `pipeline/engines.py`.

**Почему заметили поздно.** На сердце и короне разводов не было: там крупные
ровные поверхности, лоскуты выходят большими сами собой. Проявилось только
на лице - самой гладкой и самой придирчивой к чистоте поверхности.

## Обрезанный фрагмент превращается в плоскую карточку

**Симптом.** Из фотографии фигуры целиком выходит нормальная объёмная модель.
Из неё же, обрезанной по голову, - плоский билборд с напечатанной картинкой.
Альфа-канал при этом верный, силуэт вырезан чисто.

**Причина.** Не в подготовке кадра. Модель обучалась на рендерах **целых**
предметов и объём выводит по подсказкам: плечи, складки одежды, светотень.
У тесно обрезанной головы в рисованном стиле таких подсказок почти нет -
лицо нарисовано плоской заливкой. Не найдя признаков глубины, модель выбирает
самое согласованное с одним ракурсом объяснение: плоскость.

То же самое было на фрагменте кирпичной стены из набора примеров - его
свернуло в бочку. Общее у обоих случаев одно: **фрагмент, а не предмет**.

**Лечение.** Резать не по границе интересующей части, а так, чтобы вышел
самостоятельный объект. Голова - плохо, бюст с плечами и воротником - хорошо:
это привычный тип 3D-модели, и подсказки об объёме на месте.

Мелкий вырез стоит заранее увеличить до 512 по короткой стороне: кодировщик
всё равно приведёт к этому размеру, но своей интерполяцией и после потери.

**Симптом.** `1024_cascade` падает с кодом 137. Видеопамяти при этом занято
меньше четырёх гигабайт из двенадцати.

**Причина.** 137 - это SIGKILL от системного oom-killer, то есть кончилось
**обычное ОЗУ**, а не видеопамять. В логе ядра:
`Out of memory: Killed process (python) anon-rss:9682816kB` при потолке WSL
в 10 ГБ. Показательно, где именно: обе стадии выборки прошли до конца,
процесс умер в `cumesh/remeshing.py` - то есть модель 1024 карте по силам,
не помещается **постобработка**, строящая сетку из объёма.

**Что НЕ помогает.**

*Урезать `max_num_tokens` вдвое* - запускается и отрабатывает, но результат
негодный: цвет выцветает, по поверхности идёт мелкая рябь. Текстурной стадии
не хватает токенов, и она выдаёт шум вместо заливки. Проверено рендером бок
о бок с 512 - разница видна сразу.

*Поднять `vm.swappiness` до 100* - не спасает. Память растёт быстрее, чем
ядро успевает вытеснять; своп остаётся почти нетронутым, oom-killer
срабатывает раньше.

**Лечение.** Остаться на 512. Он даёт 293 тысячи граней за шесть минут при
пике 2.62 ГБ видеопамяти, и картинка честная. Для 1024 нужно больше ОЗУ:
потолок WSL с 10 до 12–13 ГБ (физических 16), и это отдельное решение -
Windows останется с четырьмя.

**Общий вывод.** Когда упёрлось, полезно спросить, во что именно. Здесь всё
указывало на видеокарту, а виновата была системная память - и лечение у этих
двух случаев совершенно разное.

## Требование к видеопамяти в документации завышено втрое

**Симптом.** В README проекта сказано «нужна карта не меньше 24 ГБ», а на
руках 12.

**Причина.** Цифра относится к наивной загрузке (`pipeline.cuda()` целиком)
и к каскаду 1536³. У TRELLIS.2 стадии идут последовательно, а режим
`low_vram=True` (включён по умолчанию) возвращает каждый блок на CPU сразу
после использования. Одновременно резидентен один DiT на 1.3B - это 2.6 ГБ
в bf16.

**Замер на RTX 3060, режим 512:** пик 2.62 ГБ из 12. Вчетверо меньше
паспортного минимума.

**Вывод.** Заявленные требования к железу проверять замером. Читать не только
README, но и код: `low_vram` нашёлся именно там, и он менял всю постановку
задачи.

## Фоновая задача рапортует об успехе, а сборка упала

**Симптом.** Запуск в фоне завершился с кодом 0, а образа нет и в логе
`ERROR: failed to build`.

**Причина.** Обёртка вида
`wsl -e bash -lc 'docker build ... > log 2>&1; echo "exit=$?" >> log'`.
Код возврата всей строки берётся у **последней** команды, то есть у `echo`,
а он успешен всегда. Настоящий код ушёл внутрь файла и никем не читался.

**Лечение.** Либо не добавлять ничего после команды и смотреть код возврата
самой обёртки, либо явно его пробрасывать: `... ; rc=$?; echo "exit=$rc"; exit $rc`.
Шире: **признак успеха у фоновой задачи проверять по её результату**
(появился ли образ, файл, строка в логе), а не по коду возврата обёртки.

## Имя пакета не совпадает с именем модуля

**Симптом.** `pip install` прошёл, `ModuleNotFoundError: No module named 'flexgemm'`.

**Причина.** Колесо называется `flex_gemm`, а `nvdiffrec` из ветки renderutils
ставится вообще как `nvdiffrec_render`. Список имён для проверки был написан
по памяти.

**Лечение.** Не перечислять имена руками, а брать их у самих пакетов:
`importlib.metadata.distribution(...).read_text("top_level.txt")`, при его
отсутствии - по корневым папкам из `dist.files`. См. `docker/verify_ext.py`.

## Импорт CUDA-расширения падает при сборке образа

**Симптом.** `RuntimeError: 0 active drivers ([]). There should only be one.`
на шаге проверки внутри `docker build`, хотя расширение только что собралось.

**Причина.** Флаг `--gpus` есть у `docker run`, но не у `docker build`. Во
время сборки видеокарты в контейнере нет, и модуль, поднимающий контекст CUDA
прямо при импорте, обязан падать.

**Лечение.** Два режима проверки. При сборке отсутствие драйвера считать
отложенной проверкой (несовпадение ABI и недостающие символы ловятся и без
видеокарты - ради этого шаг и нужен), а строгий прогон делать в рантайме:
`docker run --gpus all ... verify_ext.py --strict`.

## Модель исчезает, стоит отлететь от неё подальше

**Симптом.** В свободной камере вьюера модель пропадает целиком на расстоянии
около четырёх своих габаритов. Ошибок нет, вьюер работает, экран пустой.

**Причина.** `model-viewer` не пересчитывает ближнюю и дальнюю плоскости при
движении камеры. Он делает это **один раз, на смену `max-camera-orbit`**:
`far = 2·max(радиус габаритной сферы, максимальный радиус орбиты)`,
`near = far/1000`. При `auto` максимальный радиус равен дистанции
кадрирования, поэтому у метровой модели `far` вышел 4.76 м — дальше начинается
отсечение. Свободная камера при этом двигает не радиус, а цель, так что
пересчёт не срабатывает вовсе.

**Лечение.** На время режима задать радиус в `max-camera-orbit` явно, исходя
из нужной дальности (здесь — десять габаритов модели: `far` 20 м, `near`
2 см, вплотную подойти по-прежнему можно), и **не пускать камеру за предел**,
считая его из фактического `camera.far`. Молчаливое исчезновение модели
читается как поломка вьюера и уводит диагностику совсем в другую сторону.

## Модуль не исполнился, ошибки в консоли нет

**Симптом.** `<script type="module">` подключён, файл отдаётся с кодом 200,
но код в нём не выполняется: объект, который он кладёт в `window`, попросту
отсутствует. В консоли ни ошибки, ни предупреждения.

**Причина.** Оборвался **граф импортов**, а не сам файл. Минифицированная
сборка three разложена на два файла, и `three.module.min.js` первой строкой
импортирует `./three.core.min.js` рядом с собой. В вендоринг его не

**Лечение.** Проверять модуль **по сети, а не по консоли**: список запросов
показывает и 404, и то, какой файл его запросил. При вендоринге ES-модулей
брать не «главный файл», а замыкание списка импортов — включая относительные
(`./three.core.min.js`, `../utils/BufferGeometryUtils.js`).

## Внутри помещения всё белое, и от света это не зависит

**Симптом.** Прогулка по замкнутой локации: кадр выжжен в белое на 89%
площади. Гашение солнца не меняет ничего вообще — та же засветка.

**Причина.** Карта окружения. `scene.environment` **не знает про затенение**:
она светит на все поверхности одинаково, снаружи там стена или нет. Студийная
панорама проекта яркая намеренно (28% пикселей ярче единицы, источники до 26),
и внутри коробки это ровный белый свет сквозь стены.

**Лечение.** Локации дают освещение сами, поэтому долю окружения им надо
резать. Подобрано замером средней яркости кадра из середины коридора:

| доля окружения | 1 | 0.5 | 0.25 | 0.12 | 0.06 | 0.03 | 0 |
|---|---|---|---|---|---|---|---|
| яркость | 0.94 | 0.88 | 0.61 | 0.31 | 0.17 | 0.10 | 0.03 |
| выжжено, % | 89.2 | 50.0 | 0.3 | 0.1 | 0.1 | 0.1 | 0.1 |
| черноты, % | 0 | 0 | 0 | 0 | 0 | 10.5 | 33.3 |

Взято 0.08. **Отдельно про замер:** снимать яркость надо рендерером ТОЙ ЖЕ
сцены. Второй `WebGLRenderer`, заведённый ради замера, показывал 0.03 вместо
0.94 — карта окружения принадлежит контексту того рендерера, который её
создал, и в чужом контексте мертва. Диагноз по этим цифрам был ровно
обратным правде.

## Помещение целиком в тени, хотя источник света есть

**Симптом.** Направленный свет включён, тени включены, а вся сцена тёмная,
и яркость не меняется от интенсивности источника в тысячи раз.

**Причина.** Две, обе про тени. Первая: у `DirectionalLight` рамка карты
теней по умолчанию **±5 м**, и всё, что дальше, считается затенённым —
пятнадцатиметровый коридор попадал в тень целиком. Вторая: карта теней не
знает про прозрачность, поэтому стёкла в окнах перекрывали единственный
источник света наглухо.

**Лечение.** Рамку тени задавать по габариту сцены
(`shadow.camera.left/right/top/bottom`, затем `updateProjectionMatrix()`),
а прозрачным мешам снимать `castShadow`. Признак прозрачности брать у
материала: `transparent`, `transmission > 0` или `opacity < 1`.

## Октодерево столкновений вешает вкладку на минуты

**Симптом.** `new Octree().fromGraphNode(scene)` на модели из TRELLIS не
возвращается. Страница не отвечает, вкладка «зависла».

**Причина.** Цена сборки нелинейна и зависит от плотности сетки, а не только
от числа треугольников: ровная сфера идёт по 12 мкс на треугольник (16 000 →
199 мс), а скан — по 98 мкс (40 000 → 3.9 с), потому что мелкие треугольники
попадают сразу во много узлов и дерево дробится глубже. На 296 000
треугольников это больше двух минут.

**Лечение.** Разделить сцены по происхождению: рукотворные лёгкие (до ~12 000
треугольников) сталкивать по геометрии, сканы — по габаритному ящику, и
показывать в интерфейсе, каким коллайдером сейчас пользуешься. Шире:
**цену библиотечной функции мерить на своих данных**, а не на её примерах —
пример `games/fps` работает с уровнем в двадцать тысяч треугольников.

## Камера от первого лица «вязкая», а мир прыгает из стороны в сторону

**Симптом.** В свободной камере вьюера поворот мыши швыряет картинку рывками,
а движение вперёд ощущается как ход по пояс в воде. При этом никакой задержки
в коде нет: демпферы выставлены на ноль, ошибка положения камеры за кадр —
ровно 0.00000, кадр стоит 0.04 мс.

**Причина.** Поле зрения. `model-viewer` подбирает его кадрированием — таким,
чтобы модель заполнила кадр, — и это оказался телеобъектив: **30°**. При
постоянной чувствительности мыши один её пиксель сдвигал мир на 4.4 экранных
(полный разворот в ширину кадра — 238 пикселей против ~714 в обычном шутере),
а сжатая длинным фокусом перспектива гасила ощущение движения вперёд.

**Лечение.** На время режима обзор 65°, а чувствительность считать **от
фактического поля зрения**, а не в радианах на пиксель: 600 пикселей мыши на
поворот в высоту кадра, то есть 1.14 экранного пикселя на мышиный. Шире:
жалоба на «лаг» не обязана означать задержку — сначала проверь, сколько
экрана приходится на единицу ввода.

## Число в атрибуте lit после `removeAttribute` становится `null`

**Симптом.** Сохранённое «как было» состояние `model-viewer` восстановлено,
а камера после выхода из режима дёргается рывками вместо плавного хода.

**Причина.** Числовое свойство lit конвертирует атрибут как `Number(value)`,
но снятый атрибут даёт не значение по умолчанию, а `null`. Внутри
`interpolation-decay` превращается в `1/Math.max(0.001, null)` — время
сглаживания становится нулевым навсегда.

**Лечение.** Сохранять и восстанавливать **свойства, а не атрибуты**
(`v.interpolationDecay`, `v.interactionPrompt`, `v.cameraControls`).
Атрибут оправдан только там, где его читает кто-то ещё: состояние
автовращения кнопка ⟳ смотрит через `hasAttribute`.

## Объёмная дымка в мире гасит солнце до чёрного кадра

**Симптом.** В сцену добавлен Volume Scatter — кадр становится **полностью
чёрным**. Не тусклым, а чёрным: ни солнечных пятен, ни окон. Плотность
задана мизерная (0.0012), уменьшение её ничего не меняет.

**Причина.** Объём был повешен на **мир**, а мир в Cycles бесконечен.
Солнце — направленный источник из бесконечности, и его луч до сцены проходит
бесконечную толщу среды. Ослабление `exp(-d·L)` при `L→∞` обнуляет прямой
свет при любой сколь угодно малой ненулевой плотности. Заливка неба гаснет
по той же причине.

**Лечение.** Держать среду в **ограниченном** объёме: коробка по внутренним
размерам помещения, материал только с Volume-выходом, поверхности нет. Толща
конечна, солнце доходит, лучи видны. Плотность там нужна на порядок выше
(0.01 против 0.0012): бесконечная среда гасила не потому, что была густой.

Второе, парное: `scene.cycles.volume_bounces` по умолчанию **0**, и тогда
рассеянный внутри среды луч просто гибнет. Дымка работает поглотителем —
картинка темнеет, а лучей не появляется. Ставить хотя бы 2.

## Перспектива прячет, куда на самом деле лёг свет

**Симптом.** В кадре коридора солнечные пятна от дальних окон отсутствуют,
у ближних есть. Похоже на неудавшуюся булеву операцию: проёмы вроде бы есть,
а света из них нет.

**Причина.** Ложная тревога, и это самое дорогое в ней. В перспективе дальняя
половина сжата к точке схода: пятно шириной полтора метра занимает там
десяток пикселей и сливается с полом. «Пятна нет» и «пятно мелкое» с одного
ракурса неразличимы.

**Лечение.** Диагностический ортографический план сверху со снятым потолком
(`--plan` у `pipeline/blender/corridor.py`). На нём сразу видно: работают все
четыре окна, а тёмный дальний конец — следствие того, что окна там просто
кончились. Проверять раскладку света надо ракурсом, где она не искажается,
а не тем, который снимаем.

## Порог, назначенный из общих соображений, бракует годные кадры

**Симптом.** Проверка кадра `check_photo` задумывалась с шестью правилами.
Два из них на замерах оказались пустышками, а одно — вредным.

**Причина.** Пороги были выставлены до того, как их проверили на кадрах с
известным исходом. Замер на двенадцати примерах репозитория TRELLIS и своих
снимках показал:

* **«плоский предмет» по силуэту не определяется вовсе.** Единственный кадр,
  который заведомо провалился (`ex01`, фрагмент стены с лозами), по всем
  геометрическим признакам неотличим от удавшихся: заполнение рамки 0.56
  против 0.24 у ажурного растения `ex03` и 0.83 у диорамы комнаты `ex05` —
  обе вышли хорошо. Правило «заполнение рамки > 0.9» не сработало бы на
  негодном кадре и придиралось бы к годным;
* **дисперсия лапласиана — не детектор размытия.** `demo_heart.png` даёт 27
  при совершенно резком контуре: он просто залит ровным цветом. Порог на этой
  величине браковал бы чистые студийные снимки, которые как раз выходят
  лучше всего. Разброс у примеров — от 384 до 7251;
* **число связных кусков маски ничего не говорит о числе предметов.** У
  ажурного растения маска честно распадается на 349 кусочков. Признаком
  служит только второй КРУПНЫЙ кусок — от 5% площади.

Уцелели три правила: мелкий предмет в кадре, силуэт меньше 320 точек по
меньшей стороне, силуэт выходит за край кадра. Последнее разделяет чисто:
у всех двенадцати примеров ровно 0.000, у обрезанных портретов 8–22%.

**Лечение.** Не изобретать порог, пока нет кадров с известным исходом, на
которых он проверен. Чего числа не ловят — показывать картинкой и отдавать
на глаз: `check_photo` возвращает силуэт на шахматке, и плоская стена на нём
видна сразу, хотя ни одно число её не выдаёт.

## Второй скрипт не видит `state` из первого, хотя функции видит

**Симптом.** `nav.js` подключён после `app.js`. `window.select` — функция,
всё работает. `window.state` — `undefined`, хотя в `app.js` это переменная
верхнего уровня. Ошибка тихая: проверка вида
`if (window.state?.selectedId !== id) select(id)` не падает, а всегда даёт
истину, и почти всё продолжает работать — просто чуть больше, чем надо.
Заметно стало только по тому, что заголовок раздела отставал на одну модель.

**Причина.** В классическом скрипте свойствами `window` становятся только
`var` и объявления функций. `const` и `let` верхнего уровня живут в
лексическом окружении скрипта, а не в объекте глобали. В `app.js`
объявлено `const state = {...}` — снаружи его не достать вовсе.

**Лечение.** Не подсматривать в чужие переменные. Своё состояние держать у
себя, а нужные события получать явно: `app.js` рассылает `photo3d:state`
через `dispatchEvent`, а выбор модели перехватывается подменой
`window.select` — с функцией такой приём работает, потому что объявление
функции и свойство `window` — одна и та же ячейка.

## Сборка списка моделей подвешивает сервер на своём же опросе

**Симптом.** Страница отзывается рывками, раздача GLB ждёт непонятно чего.
Замер: отпечаток состояния — 0.21 с, полная пересборка списка — 0.76 с,
при опросе SSE раз в 0.8 с.

**Причина.** Две сложились вместе. Первая: обход шёл в цикле событий, и
всё остальное стояло, пока он идёт. Вторая: на drvfs (`/mnt/d`) один `stat`
стоит миллисекунды, а отпечаток перебирал `views/*.png` — два десятка
файлов на модель, четыре сотни на библиотеку, и так каждые 0.8 с.

**Лечение.** Три шага, каждый замерен, а не предположен:

1. обход вынесен в поток (`anyio.to_thread.run_sync`) — цикл событий свободен;
2. перебор кадров заменён одним `stat` каталога `views/`. Замер до замены:
   19 папок перебором — 51 мс, по одному `stat` — 17 мс. Замена корректна,
   потому что **mtime каталога на drvfs меняется при создании и удалении
   файла** — это проверено отдельно, а не выведено из общих соображений
   (правка файла на месте его действительно не меняет, но кадры только
   дописываются);
3. карточка модели пересобирается, только если её отпечаток изменился.

Итог: 0.13 с и 0.27 с, и обе цифры больше не в цикле событий.

Общее правило для этого проекта: **на drvfs `stat` — дорогая операция.**
Всё, что выполняется по таймеру, стоит считать в количестве `stat`, а не
в количестве строк кода.

## Внутри локации всё белое, хотя окружение уже приглушено

Симптом тот же, что в «Внутри помещения всё белое, и от света это не зависит»,
но причина другая — на ней стоит остановиться отдельно, потому что первая
проверка (доля `scene.environment`) здесь ничего не находит.

**Симптом.** Прогулка по коридору: ровное белёсое поле во весь экран, ни пола,
ни стен, ни окон. Свет ни при чём — гаснет он или нет, картинка та же.
Столкновения при этом работают, панель показывает верные габариты, ошибок в
консоли нет.

**Причина.** Дымка в воздухе — это **коробка во всю длину прохода** с
`Volume Scatter` и **без поверхности** (см. «Объёмная дымка в мире гасит
солнце до чёрного кадра»: конечный объём — единственный способ получить лучи
из окон). Cycles смотрит сквозь неё, а glTF объёмов не знает вовсе. Экспортёр
выгружает коробку обычным мешем, материал без поверхности получает белый цвет
по умолчанию формата, и `doubleSided` у него `true` — потому что в Blender у
материала по умолчанию выключено отсечение задних граней. Человек в прогулке
стоит **внутри непрозрачного белого ящика** и видит только его изнанку.

Проверяется в файле, а не на глаз: у `haze` в GLB `baseColorFactor` нет,
`doubleSided: true`, габарит примитива 3.1 × 3.5 × 15 — ровно внутренний
объём коридора.

**Лечение.** Не выгружать объекты, у которых **все** материалы объёмные
(`drop_volume_only` в `export_glb.py`). Признак объёмного материала —
у узла Material Output вход `Surface` не подключён. Проверка нужна общая, а не
по имени `haze`: любой туман, дым или подсветка объёмом попадут в ту же яму.

Общее правило: **у glTF нет объёмов.** Всё, что в Blender существует только
как Volume, при экспорте либо исчезает, либо превращается в геометрию — и
второе хуже первого, потому что выглядит как поломка вьюера.

## Процедурный материал уезжает в glTF не средним цветом, а белым

**Симптом.** Модель, отлично выглядящая в рендере Cycles, в GLB совершенно
белая. Ожидание — «ну, потеряется рисунок, останется усреднённый цвет».

**Причина.** Экспортёр glTF не сворачивает узлы в число. Встретив на входе
`Base Color` цепочку из шумов, он **выбрасывает вход целиком** — в файле не
появляется ни текстуры, ни `baseColorFactor`, а по спецификации отсутствующий
`baseColorFactor` означает белый. Замер на коридоре: из одиннадцати материалов
цвет пережили экспорт **три** — ровно те, где он был константой.

**Лечение.** Запечь материалы в текстуры до экспорта — `bake_scene.py`
(развёртка на материал, разрешение от площади, `pass_filter={"COLOR"}`,
картинки проверяются по разбросу пикселей). Постоянные материалы запекать не
надо: константа в glTF доезжает целой и весит ноль.

Косвенный признак беды, видимый без вьюера: в GLB **ни одной картинки**
(`images: 0`) при непустом списке материалов.

## Godot в `--headless` молча висит на снятии кадра

**Симптом.** Скрипт, снимающий кадр из сцены, не печатает ничего и не
завершается: 180 секунд без единой строки вывода, процесс приходится убивать.
Ни ошибки, ни предупреждения. Тот же скрипт с окном отрабатывает за две секунды.

**Причина.** `--headless` поднимает пустой драйвер отрисовки. Кадров не
рисуется вовсе, поэтому `await RenderingServer.frame_post_draw` не
разрешается **никогда**, а весь код после него не исполняется — включая
печать, по отсутствию которой и ищут причину.

Чтение ресурсов при этом работает: импорт ассетов и разбор геометрии
отрисовки не требуют и в headless проходят нормально (замер: 63 МБ ассетов —
25.9 с).

**Лечение.** Кадры снимать запуском **с окном**: на RTX 3060 полный цикл
«старт движка → загрузка сцены → снимок → выход» укладывается в 2.2–4.4 с.
Разбор геометрии оставить в headless. И в любом ожидании кадров держать
сторож по счётчику: не нарисовалось двенадцати кадров за двадцать секунд —
сказать вслух и выйти с ненулевым кодом, а не ждать до убийства процесса.

Шире: **ожидание события — это ставка на то, что событие вообще случится.**
Там, где событие даёт подсистема, которой может не оказаться, ожидание нужно
ограничивать по времени.

## `wsl` из Git Bash не находит путь, а ошибка написана кракозябрами

**Симптом.** `wsl --cd /mnt/d/Develop/photo3d -e python -m ...` отвечает
`Wsl/ERROR_PATH_NOT_FOUND`, причём русский текст ошибки приходит нечитаемым.
Та же команда, набранная в самой WSL, работает.

**Причина.** Git Bash (MSYS2) переписывает аргументы, похожие на пути POSIX,
в виндовый вид **до** запуска программы: `/mnt/d/Develop/photo3d` уезжает в
`D:\...`, и WSL получает путь, которого у неё нет. Кракозябры — отдельное
следствие: `wsl.exe` печатает UTF-16, а консоль ждёт однобайтную кодировку.

**Лечение.** `MSYS2_ARG_CONV_EXCL='*' wsl --cd ... -e ...` — переписывание
отключается целиком. Родственная грабля про PowerShell записана выше; общее
у них то, что **команду для WSL калечит не WSL, а оболочка, из которой её
запускают.**

## Локация из Blender заливает сцену белым, свет тут ни при чём

**Симптом.** GLB локации, собранной в Blender, в Godot выгорает в белое: пол
и ближняя стена без единого оттенка, текстур не разглядеть. Убавление
собственного света сцены не помогает вовсе — кадр не меняется. Первая мысль
«текстуры не доехали» неверна: кадр без освещения (`DEBUG_DRAW_UNSHADED`)
показывает и доски пола, и штукатурку.

**Причина.** Солнце приезжает **внутри GLB**, и его яркость — 28 686.
Blender пишет силу источника в физических единицах (люксах), glTF их так и
хранит, а Godot по умолчанию читает это число как обычный множитель
`light_energy`, где нормой считается около единицы. Источника в тексте сцены
не видно — он внутри ассета, поэтому и правится не там, где ищут.

**Лечение.** Перебить яркость в самой сцене, не трогая экспорт: в GLB
значение физически верное, и веб-прогулке оно не мешает.

```
[node name="sun" parent="Location" index="0"]
light_energy = 1.6
...
[editable path="Location"]
```

Шире: **свет, приехавший внутри ассета, невидим в тексте сцены.** Поэтому
`shot_scene` печатает яркость каждого источника рядом с кадром — по одной
картинке пересвет неотличим от потерянной текстуры, а по числу 28 686
причина видна сразу.

## Внутри помещения темно, хотя солнце направлено прямо в окна

**Симптом.** Солнце в сцене есть, направление верное, яркость разумная — а в
коридоре сумерки, и на полу ни одного пятна света. Подбор угла не помогает:
пятна либо не появляются, либо уезжают на стену под потолком.

**Замер, который отделяет одно от другого.** Выключить у источника
`shadow_enabled` и снять кадр ещё раз. Разброс яркости 0.459 с тенями против
**0.979 без них** — значит, свет в помещение попадает, и виновата не
геометрия света, а то, что всё внутри стоит в тени.

**Причина.** Оконное стекло уехало в GLB **непрозрачным**. В файле у материала
`glass` стоит `alphaMode=OPAQUE` и `baseColorFactor[3]=1.0`: экспортёр glTF не
умеет Glass BSDF и выдал обычный непрозрачный материал. Для отрисовки и для
теневой карты окно после этого — сплошная стена.

**Лечение.** Прозрачность задавать так, как её понимает формат: Principled с
`Alpha < 1` и blend-режимом, тогда в glTF появится `alphaMode=BLEND`. В сцене
дополнительно снимается тень с прозрачных мешей (`game/scripts/location.gd`) —
признака «не отбрасывать тень» в glTF нет вовсе, и довезти его нечем.

Родня уже записанной грабли про процедурные материалы: **glTF знает только
Principled с картинками и константами**, и всё остальное он не сворачивает,
а молча заменяет на своё умолчание.

## Игрок проваливается сквозь пол на двести метров

**Симптом.** Сцена собрана, столкновения у ассета есть, а игрок при запуске
летит вниз и не останавливается. По кадру видно только черноту, и поиск
уходит в сторону света.

**Причина.** Точка появления оказалась ЗА пределами локации. Коридор тянется
по z от -15.35 до 0.35, игрок стоял в z=5 — в четырёх с половиной метрах за
торцом, над пустотой.

**Лечение.** Проверять физику пошаговым прогоном, а не глазами:
`python -m bridge.walk_probe walk 300` ведёт игрока программно и печатает, на
каком шаге он встал на опору, сколько прошёл и **из чего состоят тела
столкновений с их габаритами**. Именно последнее и показало, что пол есть, он
верного размера, а игрок просто стоит не там.

Шире: у ассета и у сцены разные системы координат в голове у человека.
Габариты тела столкновений — единственный способ узнать, где на самом деле
находится «внутри».

## Скрипт PowerShell рушится на кириллице в собственном тексте

**Симптом.** `.ps1` с русскими строками и комментариями не запускается:
`Missing ')' in function parameter list`, `The string is missing the
terminator`. В сообщении об ошибке текст выглядит как «photo3d вЂ” РїСЂРѕРіСѓР»РєР°».

**Причина.** Windows PowerShell 5.1 читает файл скрипта **в системной
однобайтной кодировке**, если в начале нет BOM. Файл, записанный в UTF-8 без
BOM (а так пишет большинство редакторов и инструментов), разбирается как
cp1251: каждый русский символ превращается в пару-тройку мусорных, кавычки и
скобки перестают сходиться.

**Лечение.** Сохранять `.ps1` в UTF-8 **с BOM**:

```
$c = Get-Content -Raw -Encoding UTF8 $p
[System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding($true)))
```

Шире: это третья грабля подряд про то, что **команду калечит не адресат, а
оболочка** — PowerShell с аргументами для wsl, Git Bash с путями POSIX, и
теперь PowerShell с собственным файлом.

## Свет в сцене идёт ровно в противоположную сторону

**Симптом.** Направление источника взято из проверенного места и подставлено в
`.tscn`, а солнце светит наоборот. В помещении при этом наступает полная
темнота: снаружи свет есть, внутрь не попадает ни луча. Подъём яркости в два с
половиной раза не меняет кадр **ни на пиксель** — верный признак, что дело не в
силе, а в геометрии света.

**Как поймали.** Выключить тени и погасить рассеянный свет: в кадре останется
только прямой. Освещённой оказалась ВНУТРЕННЯЯ сторона оконной стены, то есть
свет шёл из глубины комнаты наружу, а не с улицы.

**Причина.** В `.tscn` матрица `Transform3D` записывается **строками**, а не
осями-столбцами. Базис, собранный по осям (`x_axis, y_axis, z_axis`) и
записанный в том же порядке, читается как транспонированный — а транспонирование
поворота это **обратный поворот**. Свет разворачивается на 180°.

**Лечение.** Транспонировать при записи: строка 0 это `(x.x, y.x, z.x)`, а не
`(x.x, x.y, x.z)`. Проверять не глазами, а кадром без теней и без рассеянного
света — на нём видно, какая поверхность ловит прямой луч.

Шире: **у матрицы поворота ошибка транспонирования не выглядит как ошибка.**
Она даёт правдоподобную картинку, просто не ту, и ищут её обычно в свойствах
света, где её нет.

## Правка цвета текстуры в шейдере не доезжает до игры

**Симптом.** Скан подкрашен множителем прямо в материале — в Blender видно, в
рендере видно, — а в игре поверхность прежнего цвета. Пересборка и повторный
импорт ничего не меняют.

**Причина.** Экспортёр glTF берёт из материала только то, что формат умеет:
картинку на входе и **константу** множителем к ней. Узел между текстурой и
`Base Color` — Mix, Multiply, что угодно — он не сворачивает в число, а
**выбрасывает целиком**. В файле после этого нет ни правки, ни
`baseColorFactor`, то есть множитель равен белому.

**Как проверить.** Открыть GLB как JSON и посмотреть материал:

```
baseColorFactor: None   ->  правка не доехала, цвет исходный
```

**Лечение.** Тон сцены сводить **светом** — цветом солнца и рассеянного света
в `.tscn`, где его видно и где он экспорт переживает. Нужен именно другой цвет
поверхности — красить саму картинку на диске, а не узлами в шейдере.

Третий случай одной и той же болезни (первые два: процедурные материалы и
стекло). Общее правило: **всё, что не картинка и не константа, glTF молча
заменяет своим умолчанием.**


## Генерация идёт вчетверо дольше, чем должна, а видеокарта почти простаивает

**Симптом.** `photo_to_3d` идёт пятнадцать минут вместо семи. Видеокарта при
этом занята на треть: пик 3.85 ГБ из 12. Ошибок нет, ничего не падает, время
от прогона к прогону скачет вдвое без видимой причины.

**Как поймать.** Сэмплеры TRELLIS печатают собственный прогресс. Сложить их
время и сравнить с заявленным этапом:

```
Sampling sparse structure  12/12  21 с
Sampling shape SLat        12/12  47 с
Sampling texture SLat      12/12  24 с
"генерация_с": 576.1
```

92 секунды счёта внутри этапа на 576 секунд. Остальное — не вычисления.

**Причина.** Штатный загрузчик `trellis2/models/__init__.py` сначала создаёт
модуль со случайными весами, потом рядом читает файл, потом копирует одно в
другое: двойной пик оперативной памяти на каждую модель и 9.22 ГБ постоянно
занятыми на шести. В WSL доступно 9.95 ГБ. Дальше режим `low_vram` перед
каждым этапом делает `.to('cuda')`, после — `.cpu()`, и гоняет через шину
21 ГБ, половина которых лежит в подкачке. Замер: при загрузке в подкачку
уходит 3.8 ГБ.

Диск тут ни при чём — его проверили отдельно: 564 МБ/с подряд, 353 МБ/с
блоками по 4 КБ. Девять гигабайт обязаны читаться за двадцать секунд.

**Лечение.** `patch_lazy_weights()` в `pipeline/trellis/run_trellis.py`:
модули собираются на устройстве `meta` (форма и тип без данных), а веса
читаются с диска прямо в видеопамять ровно на время своего этапа. Оперативная
память под веса не нужна вовсе.

Замер конца в конец на том же входе и том же seed: **923 → 225 с**. Пик
видеопамяти не изменился (3.85 ГБ — там и раньше жила одна модель за раз),
картинка результата совпадает.

**Общее правило.** Когда время скачет вдвое от прогона к прогону, а нагрузка
на считающее устройство низкая — ищи не медленный алгоритм, а память, которой
не хватило на полшага.


## После сборки на `meta` модель падает в forward, хотя все параметры на месте

**Симптом.** Модель собрана на `meta`, веса загружены, проверка «не осталось
ли чего на meta» проходит чисто — а `forward` падает:

```
NotImplementedError: Cannot copy out of meta tensor; no data!
  .../modules/sparse/attention/rope.py, line 24
      self.freqs = self.freqs.to(indices.device)
```

**Причина.** Тензор лежит **простым атрибутом**, а не через
`register_buffer`. Такие тензоры не попадают ни в `state_dict()`, ни в
`named_buffers()` — то есть их не видит ни загрузка весов, ни перенос между
устройствами, ни проверка. У `SLatFlowModel` таких по тридцать штук на модель.

**Лечение.** Искать их обходом модулей по `vars(mod)`, а не через API
параметров:

```python
for path, mod in model.named_modules():
    reserved = set(mod._parameters) | set(mod._buffers)
    for name, value in vars(mod).items():
        if isinstance(value, torch.Tensor) and name not in reserved:
            ...  # это тоже надо пересадить
```

**Общее правило.** `state_dict()` — это не «всё содержимое модели», а только
то, что автор решил сохранять. Проверка полноты по нему неполна по
построению.


## `assign=True` в `load_state_dict` меняет тип слоёв и роняет счёт

**Симптом.** Веса загружены из того же файла, что и раньше, а модель падает:

```
RuntimeError: mat1 and mat2 must have the same dtype, but got Float and BFloat16
```

**Причина.** Обычный `load_state_dict` **копирует** данные в уже созданные
параметры и потому сохраняет тип, который задал конструктор. `assign=True`
отдаёт модулю тензоры из файла как есть — вместе с их типом. Для модели
смешанной точности это разные вещи: часть слоёв живёт в fp32, а чекпойнт
хранит всё в bf16.

**Лечение.** Снять задуманные типы с модели, пока она пуста, и приводить к ним
при загрузке. Сборка на `meta` для этого и годится: данных нет, а форма и тип
есть.

```python
dtypes = {k: v.dtype for k, v in model.state_dict().items()}   # на meta
...
state[k] = v.to(dtypes[k])                                     # перед assign
```

**Общее правило.** Ускорение, которое трогает типы, обязано сверяться с тем,
что было до него. Здесь спасло то, что модель упала сразу; молча разошедшаяся
точность стоила бы куда дольше.


## Исполнителей заданий оказывается двое, и оба лезут в видеокарту

**Симптом.** Пока идёт генерация, рядом поднимается второй воркер и берёт
следующее задание. Две генерации по 9.13 ГБ весов в 10 ГБ памяти WSL — обе
уходят в подкачку и считаются втрое дольше либо падают по OOM.

**Причина.** Замок воркера держится сердцебиением: файл со временем
последнего удара, старше двадцати секунд — процесс считается мёртвым. Удар
стоял в главном цикле, а главный цикл на время задания уходит внутрь
`engine.generate` на четыре минуты. То есть ровно тогда, когда воркер занят
по-настоящему, он и выглядит мёртвым, а `ensure_worker` честно поднимает
замену.

**Лечение.** Бить из отдельного потока (`Heart` в `worker/main.py`), который
живёт весь срок процесса и не зависит от того, чем занят главный. Заодно этот
поток следит, не перехватил ли замок кто-то ещё.

**Общее правило.** Сердцебиение обязано идти по своим часам, а не по ходу
работы, которую оно охраняет: иначе оно замолкает именно в тот момент, ради
которого заводилось. Поймано до первого прогона — сверкой BEAT_SEC (3 с) со
временем генерации (250 с), а не по факту двух генераций разом.


## Замок в наблюдаемой папке сбивает дешёвую проверку изменений

**Симптом.** Воркер и веб перебирают всю очередь по нескольку раз в секунду,
хотя ничего не менялось.

**Причина.** И тот и другой сначала смотрят mtime папки — свойство drvfs,
замеренное для `web/app.py`: он меняется при появлении и исчезновении файла.
Замок воркера лежал там же и переписывался каждые три секунды через временный
файл и `os.replace`, то есть создавал и удалял файл в наблюдаемой папке. Папка
выглядела изменившейся всегда.

**Лечение.** Служебное — в свою подпапку (`data/jobs/worker/`), под
наблюдением остаются только сами задания. В отпечаток для SSE вместо mtime
замка попадает признак «жив»: он меняется, когда воркер появился или пропал,
а не каждые три секунды.

## Готовые кадры, сложенные в ролик, теряют насыщенность

**Симптом.** Кадры оборота в папке `views/` ярко-красные, а в собранном из них
`spin.mp4` сердце кирпичное. Геометрия, ракурсы и порядок кадров при этом
верные — «поехал» только цвет.

**Причина.** Видеоредактор Blender — часть обычного конвейера рендера, и на
выходе к пикселям применяется view transform сцены. По умолчанию это AgX,
который гасит насыщенные цвета (та же причина, по которой постановочный стиль
переключён на `Standard`). К кадрам оборота тональное отображение уже
применили при их рендере, так что второй проход — чистая потеря: AgX поверх
AgX.

**Лечение.** `scene.view_settings.view_transform = "Standard"`, `look = "None"`
в `pipeline/blender/video.py`. После правки красное 182.8, 138.3, 142.0
переносится в ролик как 182.5, 138.4, 142.2 — расхождение уровня сжатия H.264,
а не цветокоррекции.

**И отдельно — про замер.** Первая проверка показала расхождение и после
правки: 10.8 по красному каналу. Виноват был сам проверяющий скрипт — он
вытаскивал кадр из готового mp4 через тот же видеоредактор с настройками по
умолчанию, то есть добавлял AgX уже при извлечении. Инструмент проверки
подчиняется тем же правилам, что проверяемый код: расхождение может жить в
нём, а не в результате.


## Запись «через временный файл» падает, когда писателей больше одного

**Симптом.** `os.replace(tmp, path)` изредка падает с
`FileNotFoundError: '...json.tmp' -> '...json'`. Файл, который только что
записали, исчезает между записью и переименованием.

**Причина.** Приём «пишем в `<файл>.tmp`, затем `os.replace`» защищает от
обрыва записи, но не от второго писателя: имя временного файла у всех одно.
Второй процесс перезаписывает тот же `.tmp` и переименовывает его первым —
а у первого под ногами уже ничего нет. В очереди заданий писателей трое: веб,
MCP-сервер и воркер.

**Лечение.** Уникальное имя временного файла на каждую запись
(`<файл>.<pid>.<случайное>.tmp`). Тогда `os.replace` остаётся атомарным, а
исход становится тем, который и нужен: выигрывает последний записавший.
Проверено тремя процессами по 40 правок в одно задание — ошибок ноль,
временных файлов не остаётся.

**Общее правило.** Атомарность `os.replace` относится к переименованию, а не
ко всей операции записи. Как только у файла появляется второй писатель,
общее имя временного файла превращается в разделяемое состояние.

## Картинка выцветает в молоко, сколько ни убавляй свет

**Симптом.** Сцена собрана, палитра подобрана глазами (трава `0.38, 0.62, 0.25`,
песок `0.84, 0.75, 0.52`), а в кадре всё пастельное: трава салатовая, песок
белый, снег выжжен. Уменьшение яркости солнца и рассеянного света помогает
слабо и одновременно гасит тени. Вода в той же сцене выглядит нормально.

**Причина.** Цвет вершин уходит в шейдер как есть, а `ALBEDO` движок считает
**линейным**. Палитра же подбиралась в sRGB — как её видит глаз и пипетка.
Зелёный `0.38`, попав в линейное пространство, соответствует sRGB-яркости
около `0.65`: цвет становится вдвое светлее и заметно бледнее. У воды того же
не случилось, потому что её цвета приходят через `uniform vec3 : source_color`,
а этот хинт заставляет движок перевести значение сам.

**Лечение.** `Color.srgb_to_linear()` при запекании цвета в вершины
(`game/scripts/islands/island_world.gd`), либо `source_color` на uniform-ах.
Признак, по которому диагноз ставится за секунду: **в одной сцене одни
материалы бледные, другие нет** — значит, дело не в свете и не в тонмаппинге,
а в том, каким путём цвет попал в шейдер.

## Съёмка сцены обрывается на процедурном меше

**Симптом.** `shot_scene` не возвращает ни кадра и упирается в таймаут. В
выводе движка — `Trying to assign value of type 'Nil' to a variable of type
'PackedInt32Array'` в `tools/shot.gd`.

**Причина.** Меш, собранный в коде из отдельных треугольников, живёт **без
массива индексов** — вершины идут подряд. `surface_get_arrays` кладёт в
`ARRAY_INDEX` `null`, а подсчёт треугольников присваивал его в типизированную
переменную.

**Лечение.** Проверять тип, а не полагаться на присваивание:
`if idx is PackedInt32Array and idx.size() > 0`. Шире: **`surface_get_arrays`
возвращает массив с дырами**, и любой его слот может оказаться `null` —
индексы, цвета, вторые UV.

## Пена у берега расползается на полсотни метров

**Симптом.** Шейдер воды красит прибой по глубине (`глубина < 1.5 м → пена`).
У обрыва полоса выглядит правильно, а вокруг пологого острова превращается в
белый ореол шириной в треть острова.

**Причина.** Ширина полосы задана **в метрах глубины**, а видна она **в метрах
по горизонтали**. Связь между ними — уклон дна: на склоне 1:30 полтора метра
глубины растягиваются в сорок пять метров пляжной пены.

**Лечение.** Считать расстояние до уреза воды по горизонтали:
`|высота| / |градиент высоты|` — первое приближение расстояния до нулевого
уровня, точное для линейного склона (`game/shaders/water.gdshader`). Плечо для
градиента брать шире одного тексела: билинейная фильтрация даёт производную,
постоянную внутри тексела, и по узкому плечу кромка пены получается
ступенчатой.

## Панель разделов остаётся шириной в один значок, хотя CSS верный

**Симптом.** `#rail` задан как `flex: 0 0 var(--rail)` при `--rail: 194px`.
`getComputedStyle(rail).getPropertyValue('--rail')` возвращает `194px` — а
`flexBasis` при этом `48px`, и панель нарисована сложенной. Класса
`rail-min` на `body` нет, медиазапрос не совпал. Снимаешь `transition` из
консоли — ширина немедленно становится верной.

**Причина.** Переход `transition: flex-basis .14s, width .14s`. Пока таблица
с переменными ещё не разобрана, `var(--rail)` не определена, и `flex-basis`
откатывается к `auto` — то есть к ширине содержимого, 48 пикселей. Появление
переменной браузер видит как смену значения и запускает переход. В окне,
которое не композитит кадры (свёрнутая панель, фоновая вкладка, окно вне
экрана), кадры не идут — и переход не продвигается, застревая на исходном
значении навсегда. Вычисленная переменная при этом уже правильная, поэтому
осмотр стилей уводит в сторону: ищешь ошибку в каскаде, а её там нет.

**Лечение.** Не вешать переход на размеры, которые считаются из переменных
и участвуют в первой раскладке. Ширины доков в редакторах и без того меняются
мгновенно. Шире: **застрявшее промежуточное значение — признак перехода, а не
каскада.** Проверяется в одну строку: `el.style.transition = 'none'`.

## Новый файл стилей приезжает из кэша старым

**Симптом.** Добавлен `theme.css`, в нём переменные, на которые опираются
остальные таблицы. В браузере часть правил работает, часть — нет; после
правки файла ничего не меняется. В списке `document.styleSheets` у всех
таблиц есть `?v=<время>`, и только у новой его нет.

**Причина.** `web/app.py` дописывал `?v=<mtime>` по **перечню имён, вбитому
руками**. Новый файл в перечень не попадал, оставался без метки версии и
доставался из кэша по эвристике Chromium — а она держит копию, попавшую туда
до появления `cache-control`, невзирая на обычную перезагрузку.

**Лечение.** Собирать перечень обходом папки: `STATIC.glob("*.css")` и
`STATIC.glob("*.js")`. Именно `glob`, а не `rglob`: `vendor/` трогать нельзя —
версия там прибита, а лишний параметр сломал бы карту импортов, по которой
аддоны three ищут друг друга. Шире: **список файлов, который надо не забыть
дополнить, рано или поздно не дополнят** — и сбой будет молчаливым.

## Свежая картинка в assets не существует для запущенной игры

**Симптом.** Скрипт положил PNG в `game/assets/previews/`, файл на диске есть и
открывается, а `ResourceLoader.exists("res://assets/previews/islands.png")` в
игре возвращает `false`. Лаунчер показывает «превью нет» на только что снятых
кадрах.

**Причина.** Godot работает не с исходным файлом, а с разобранным: рядом должен
лежать `.import`, а сама картинка — в `.godot/imported/`. Редактор делает это
сам при виде нового файла, но **запуск проекта (не редактора) ничего не
импортирует** — он только читает готовое.

**Лечение.** После записи ассетов извне звать движок отдельно:

```
godot --headless --path <game> --import
```

Тем же вызовом пользуется `bridge/import_asset.py`, и по той же причине.
Общее правило: **всё, что кладётся в `res://` мимо редактора, нужно
импортировать явно** — иначе оно есть на диске и отсутствует в игре.
