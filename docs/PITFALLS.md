# Грабли

Каждая запись — симптом, причина, лечение. Симптом стоит первым намеренно:
искать здесь будут по нему, а не по названию причины.

Все они настоящие: собраны по ходу работы, а не выписаны из документации.

---

## Половина pymeshlab отсутствует, PLY не сохраняется

**Симптом.** `import pymeshlab` проходит, но `meshing_close_holes`,
изотропного ремешинга и реконструкции Пуассона нет. `save_current_mesh`
падает с `Unknown format for save: ply`. В stderr — строки вида
`Cannot load library libfilter_meshing.so: (libOpenGL.so.0: cannot open shared object file)`.

**Причина.** Qt-плагины pymeshlab требуют `libOpenGL.so.0`, даже когда
ничего не рендерится. Без неё они молча не загружаются, а импорт при этом
проходит успешно.

**Лечение.** `apt-get install libopengl0`. Проверять наличие фильтра через
`hasattr(ms, name)` и сообщать о пропуске вслух, а не проглатывать.

## QuadriFlow ничего не делает, но рапортует об успехе

**Симптом.** `bpy.ops.object.quadriflow_remesh(...)` возвращает `FINISHED`,
число граней не меняется. В warning: `The mesh needs to be manifold and have
face normals that point in a consistent direction`.

**Причина.** В фоновом режиме Blender (`-b`) QuadriFlow не работает.
Проверено на заведомо чистом меше: 0 неманифолдных рёбер, 0 неманифолдных
вершин, 0 граничных, 1 остров — отказ всё равно. Воспроизводится в режимах
`FACES` и `RATIO`, через `context.temp_override` и на триангулированном входе.
Сообщение про манифолд вводит в заблуждение.

**Лечение.** Использовать Voxel Remesh — он даёт замкнутую оболочку целиком
из квадов за доли секунды. Шире: **результат операторов `bpy.ops` проверять
по счётчикам, а не по коду возврата.**

## После ремонта модель превратилась в бесформенный комок

**Симптом.** Геометрия по всем метрикам отличная — нужное число граней, все
квады, замкнутая оболочка, — а на рендере вместо объекта невнятная масса.

**Причина.** Оси при обмене через PLY. glTF хранит Y вверх, и его импортёр
разворачивает сцену в Z-вверх. PLY читается как есть, без поворота. Цепочка
GLB → pymeshlab → PLY → Blender давала модель, повёрнутую на 90°: турнтейбл
снимал её в профиль при совершенно целой геометрии.

**Лечение.** `bpy.ops.wm.ply_import(filepath=..., forward_axis="NEGATIVE_Z", up_axis="Y")`.
Шире: при обмене между форматами оси задавать явно, а результат смотреть
глазами — метрики этой ошибки не показывают вообще.

## Cycles считает на процессоре, кадр идёт 18 секунд

**Симптом.** Постановочный рендер 24 кадров занимает семь минут. В логе
`libEGL warning: failed to open /dev/dri/renderD128: Permission denied`.

**Причина.** Две независимые. Первая: пользователь WSL не состоит в группе
`render`, а узел принадлежит `root:render` с правами `crw-rw----`. Вторая:
Blender по умолчанию считает Cycles на CPU, GPU надо выбрать явно.

**Лечение.** `usermod -aG render <user>` плюс `wsl --shutdown` (без перезапуска
членство не применяется). В скрипте — выбрать устройство:
`prefs.compute_device_type = "OPTIX"` или `"CUDA"`, затем `scene.cycles.device = "GPU"`.
Итог: 45 секунд вместо 430.

## EEVEE медленнее Cycles

**Симптом.** «Быстрый» растеризатор даёт 14.3 с/кадр, трассировщик — 1.7 с.

**Причина.** В WSL EEVEE получает лишь программный GL-контекст. Cycles идёт
через CUDA и видеокарту не теряет.

**Лечение.** Для постановочных кадров первым пробовать Cycles, EEVEE держать
запасным. Общий вывод: **ожидания о производительности проверять замером.**

## Цвет выходит блёклым, не тем, что задали

**Симптом.** Заказана терракота, отрендерился бледный лосось.

**Причина.** Две сложились. Blender 4.x применяет вид `AgX`, который красиво
приглушает насыщенные цвета. И палитра была задана линейными долями «на глаз»
вместо честного перевода из sRGB.

**Лечение.** `scene.view_settings.view_transform = "Standard"` для кадров, где
важна достоверность цвета. Палитру задавать sRGB-кодами и переводить в
линейное пространство формулой.

## Элемент с атрибутом `hidden` виден на странице

**Симптом.** `el.hidden === true`, а элемент на экране. Полноэкранный оверлей
лайтбокса висит поверх всего интерфейса.

**Причина.** `hidden` задаёт `display: none` с крайне низким приоритетом,
и любое правило вроде `.lightbox { display: grid }` его перебивает.

**Лечение.** `[hidden] { display: none !important; }` в начале стилей.

## model-viewer загрузил модель, но ничего не рисует

**Симптом.** `loaded === true`, `modelIsVisible === false`, холст остался
300×150, в консоли `rAF timed out in updateSource`.

**Причина.** Окно не композитит кадры, поэтому `requestAnimationFrame` и
`ResizeObserver` не срабатывают. Ленивая загрузка и рендер завязаны на них.

**Лечение.** `loading="eager"` снимает половину проблемы. Полностью —
не лечится, это свойство среды. В интерфейсе предусмотрен откат на турнтейбл
по готовым кадрам, работающий без WebGL. Диагностический вывод: **прежде чем
чинить код, проверь, не врёт ли среда.**

## pymeshlab падает на модели с текстурой

**Симптом.** `save_current_mesh("x.ply")` бросает
`Image .../texture_0 cannot be saved. Your MeshLab version has not plugin to
save file format`, следом в консоль сыплется `malloc_consolidate(): unaligned
fastbin chunk detected`. На той же модели без текстуры всё работает.

**Причина.** Сохраняя PLY, pymeshlab пытается записать рядом и встроенную
картинку. Имя текстуры из GLB (`texture_0`) идёт без расширения, формат он не
определяет и падает — повреждая кучу в придачу.

**Лечение.** Отдавать в pymeshlab **чистую геометрию**: сначала
`trimesh.load(glb, force="mesh").export("geometry.ply")`, потом уже загружать
её. Для ремонта и ретопологии внешний вид всё равно не нужен — он переносится
отдельным шагом с оригинала.

## Canvas с `inset: 0` не растягивается на родителя

**Симптом.** Наложенная на 3D-вид сетка смещена и отмасштабирована не так,
как модель. `getBoundingClientRect()` холста показывает 300×150 при родителе
990×451.

**Причина.** Canvas — **замещаемый элемент**. У таких `width: auto` разрешается
в собственный размер содержимого, а не растягивается по `inset: 0`, как у
обычных блоков. Задание только `canvas.width` (буфера) меняет и CSS-бокс,
поэтому при `devicePixelRatio ≠ 1` бокс расходится с родителем в те же разы.

**Лечение.** Явные `width: 100%; height: 100%` в CSS. Буфер задавать
как `размер × dpr`, а рисовать через `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`
в CSS-пикселях.

**Отдельно про проверку.** Ошибку дважды пропустила проверка «центр модели
попадает в центр экрана»: центр остаётся центром при **любом** масштабе по
горизонтали, поэтому такой тест слеп к ошибкам масштаба и аспекта. Проверять
надо точки **вне** центра, а лучше — прямо сравнивать прямоугольники холста
и родителя.

## Наложенная графика не совпадает с 3D-моделью

**Симптом.** Сетка пола и круг-опора нарисованы в правильной перспективе, но
стоят не под моделью, а рядом. При панорамировании расхождение растёт.

**Причина.** Камера собиралась заново из `getCameraOrbit()` и `getCameraTarget()`.
Model-viewer вращает камеру **вокруг начала координат** и смещает саму сцену,
а не наоборот. Прибавление цели к позиции камеры даёт промах: небольшой в покое
(0.09 по Y на тестовой модели) и равный всему сдвигу после панорамирования.
Вдобавок `scene.boundingBox` хранится в своём пространстве, а в мир его
переводит `scene.target.position` — без этой поправки центр модели промахивается
мимо центра экрана.

**Лечение.** Не пересобирать камеру, а взять её у рендерера:
`viewer[Symbol(scene)].camera`, оттуда `projectionMatrix` и обратная
`matrixWorld`. Мировая точка = координата ящика + `scene.target.position`.
Тогда никакие соглашения об осях, FOV и панорамировании не имеют значения —
используется ровно то преобразование, которым рисуется модель.

Это внутренности библиотеки, и они могут измениться. Поэтому при их отсутствии
сетка не рисуется вовсе: **лучше без пола, чем пол не там, где модель.**

**Отдельный вывод про проверку.** Первая версия была проверена картой canvas
и признана рабочей: линии сходились к горизонту, перспектива считалась верно.
Но на карте была **только сетка, без модели**, поэтому несовпадение увидеть
было нечем. Проверять надо взаимное расположение, а не каждый объект отдельно:
в карту добавлена проекция габаритов модели, и центр обязан попадать в центр
экрана, а основание — внутрь круга.

## pip-пакет установился, но падает при первом вызове

**Симптом.** `rembg` ставится, при использовании — `No onnxruntime backend found`.
`trimesh.fix_normals()` — `ModuleNotFoundError: scipy`.

**Причина.** У обоих ключевые зависимости вынесены: у rembg в экстра `[cpu]`,
у trimesh графовые операции требуют scipy отдельно.

**Лечение.** `pip install "rembg[cpu]" scipy`. Шире: проверять пакет вызовом
той функции, ради которой он ставился, а не одним `import`.

## PowerShell калечит команды для wsl

**Симптом.** `wsl -e python -c "import x; print(\"y\")"` падает с
`SyntaxError: invalid syntax`, аргументы разъезжаются. `grep -r "..." $VAR/path`
с пустой переменной уходит рекурсивно обходить текущую папку.

**Причина.** Разбор аргументов нативных команд в PowerShell переставляет
кавычки непредсказуемо.

**Лечение.** Не передавать сложные строки инлайном. Класть код в файл-скрипт
и запускать его:
`wsl -e /opt/photo3d/venv/bin/python /mnt/d/.../script.py`.
Для shell-скриптов помогает `tr -d '\r' < файл | bash` — заодно снимает CRLF.

## Модель загрузилась, но у неё «нет атрибута layer»

**Симптом.** `AttributeError: 'DINOv3ViTModel' object has no attribute 'layer'`
на первой же генерации. Веса при этом читаются, архитектура сходится.

**Причина.** TRELLIS.2 обходит слои кодировщика напрямую: `self.model.layer`.
В transformers 5.x они переехали внутрь энкодера и лежат по адресу
`model.model.layer`. Репозиторий писался в ноябре 2025, библиотека с тех пор
ушла вперёд.

**Лечение.** Не откатывать библиотеку, а подменить один метод. Сигнатуры
`embeddings(pixel_values, bool_masked_pos)` и
`layer(hidden_states, position_embeddings=...)` в новой версии те же -
проверено через `inspect.signature`, - поэтому расхождение ровно одно.
См. `patch_dino_layers()` в `pipeline/trellis/run_trellis.py`: список слоёв
ищется сначала по старому адресу, затем по новому.

**Общий вывод.** Когда чужой код лезет во внутренности библиотеки, ломается
он при её обновлении, а не при своём. Прежде чем откатывать версию целиком,
стоит сравнить сигнатуры: расхождение обычно точечное.

## Модель выглядит испачканной, хотя геометрия чистая

**Симптом.** На лице и других гладких местах тёмные разводы, будто модель
уронили в грязь. Форма при этом вылеплена аккуратно.

**Как проверить.** Отрендерить глиной, без текстуры. Если разводы пропали -
дело не в геометрии, а в раскраске. Пока эту проверку не сделали, объяснения
строились вокруг формы («линии рисунка вдавливаются в рельеф») и вели не туда.

**Причина.** Развёртка строится автоматически по сетке из marching cubes:
у каждого треугольника свой лоскут, между лоскутами - незаполненный чёрный
фон. При сглаживании текстуры фон затекает внутрь лоскутов. Чем мельче
лоскут, тем больше доля затёкшего.

Считается просто: `размер_карты^2 / число_граней` - это площадь на
треугольник.

| граней | карта | пикселей на грань | вид |
|---|---|---|---|
| 300 000 | 2048 | ~14 | грязь на гладких местах |
| 80 000 | 4096 | ~210 | чисто |

**Лечение.** Не гнаться за числом граней. 80 000 на карту 4096 выглядят
заметно лучше, чем 300 000 на 2048, **при том же времени работы** и вчетверо
меньшем файле. Значения в `server/config.py`, по режимам - в `pipeline/engines.py`.

**Почему заметили поздно.** На сердце и короне разводов не было: там крупные
ровные поверхности, лоскуты выходят большими сами собой. Проявилось только
на лице - самой гладкой и самой придирчивой к чистоте поверхности.

## Обрезанный фрагмент превращается в плоскую карточку

**Симптом.** Из фотографии фигуры целиком выходит нормальная объёмная модель.
Из неё же, обрезанной по голову, - плоский билборд с напечатанной картинкой.
Альфа-канал при этом верный, силуэт вырезан чисто.

**Причина.** Не в подготовке кадра. Модель обучалась на рендерах **целых**
предметов и объём выводит по подсказкам: плечи, складки одежды, светотень.
У тесно обрезанной головы в рисованном стиле таких подсказок почти нет -
лицо нарисовано плоской заливкой. Не найдя признаков глубины, модель выбирает
самое согласованное с одним ракурсом объяснение: плоскость.

То же самое было на фрагменте кирпичной стены из набора примеров - его
свернуло в бочку. Общее у обоих случаев одно: **фрагмент, а не предмет**.

**Лечение.** Резать не по границе интересующей части, а так, чтобы вышел
самостоятельный объект. Голова - плохо, бюст с плечами и воротником - хорошо:
это привычный тип 3D-модели, и подсказки об объёме на месте.

Мелкий вырез стоит заранее увеличить до 512 по короткой стороне: кодировщик
всё равно приведёт к этому размеру, но своей интерполяцией и после потери.

**Симптом.** `1024_cascade` падает с кодом 137. Видеопамяти при этом занято
меньше четырёх гигабайт из двенадцати.

**Причина.** 137 - это SIGKILL от системного oom-killer, то есть кончилось
**обычное ОЗУ**, а не видеопамять. В логе ядра:
`Out of memory: Killed process (python) anon-rss:9682816kB` при потолке WSL
в 10 ГБ. Показательно, где именно: обе стадии выборки прошли до конца,
процесс умер в `cumesh/remeshing.py` - то есть модель 1024 карте по силам,
не помещается **постобработка**, строящая сетку из объёма.

**Что НЕ помогает.**

*Урезать `max_num_tokens` вдвое* - запускается и отрабатывает, но результат
негодный: цвет выцветает, по поверхности идёт мелкая рябь. Текстурной стадии
не хватает токенов, и она выдаёт шум вместо заливки. Проверено рендером бок
о бок с 512 - разница видна сразу.

*Поднять `vm.swappiness` до 100* - не спасает. Память растёт быстрее, чем
ядро успевает вытеснять; своп остаётся почти нетронутым, oom-killer
срабатывает раньше.

**Лечение.** Остаться на 512. Он даёт 293 тысячи граней за шесть минут при
пике 2.62 ГБ видеопамяти, и картинка честная. Для 1024 нужно больше ОЗУ:
потолок WSL с 10 до 12–13 ГБ (физических 16), и это отдельное решение -
Windows останется с четырьмя.

**Общий вывод.** Когда упёрлось, полезно спросить, во что именно. Здесь всё
указывало на видеокарту, а виновата была системная память - и лечение у этих
двух случаев совершенно разное.

## Требование к видеопамяти в документации завышено втрое

**Симптом.** В README проекта сказано «нужна карта не меньше 24 ГБ», а на
руках 12.

**Причина.** Цифра относится к наивной загрузке (`pipeline.cuda()` целиком)
и к каскаду 1536³. У TRELLIS.2 стадии идут последовательно, а режим
`low_vram=True` (включён по умолчанию) возвращает каждый блок на CPU сразу
после использования. Одновременно резидентен один DiT на 1.3B - это 2.6 ГБ
в bf16.

**Замер на RTX 3060, режим 512:** пик 2.62 ГБ из 12. Вчетверо меньше
паспортного минимума.

**Вывод.** Заявленные требования к железу проверять замером. Читать не только
README, но и код: `low_vram` нашёлся именно там, и он менял всю постановку
задачи.

## Фоновая задача рапортует об успехе, а сборка упала

**Симптом.** Запуск в фоне завершился с кодом 0, а образа нет и в логе
`ERROR: failed to build`.

**Причина.** Обёртка вида
`wsl -e bash -lc 'docker build ... > log 2>&1; echo "exit=$?" >> log'`.
Код возврата всей строки берётся у **последней** команды, то есть у `echo`,
а он успешен всегда. Настоящий код ушёл внутрь файла и никем не читался.

**Лечение.** Либо не добавлять ничего после команды и смотреть код возврата
самой обёртки, либо явно его пробрасывать: `... ; rc=$?; echo "exit=$rc"; exit $rc`.
Шире: **признак успеха у фоновой задачи проверять по её результату**
(появился ли образ, файл, строка в логе), а не по коду возврата обёртки.

## Имя пакета не совпадает с именем модуля

**Симптом.** `pip install` прошёл, `ModuleNotFoundError: No module named 'flexgemm'`.

**Причина.** Колесо называется `flex_gemm`, а `nvdiffrec` из ветки renderutils
ставится вообще как `nvdiffrec_render`. Список имён для проверки был написан
по памяти.

**Лечение.** Не перечислять имена руками, а брать их у самих пакетов:
`importlib.metadata.distribution(...).read_text("top_level.txt")`, при его
отсутствии - по корневым папкам из `dist.files`. См. `docker/verify_ext.py`.

## Импорт CUDA-расширения падает при сборке образа

**Симптом.** `RuntimeError: 0 active drivers ([]). There should only be one.`
на шаге проверки внутри `docker build`, хотя расширение только что собралось.

**Причина.** Флаг `--gpus` есть у `docker run`, но не у `docker build`. Во
время сборки видеокарты в контейнере нет, и модуль, поднимающий контекст CUDA
прямо при импорте, обязан падать.

**Лечение.** Два режима проверки. При сборке отсутствие драйвера считать
отложенной проверкой (несовпадение ABI и недостающие символы ловятся и без
видеокарты - ради этого шаг и нужен), а строгий прогон делать в рантайме:
`docker run --gpus all ... verify_ext.py --strict`.

## Команда не найдена при запуске через `wsl -e`

**Симптом.** `wsl -u root -e usermod ...` → `execvpe usermod failed 2`.

**Причина.** `-e` запускает программу напрямую, без инициализации окружения,
поэтому `/usr/sbin` в PATH отсутствует.

**Лечение.** Полный путь (`/usr/sbin/usermod`) либо `wsl -e bash -lc "..."`.
